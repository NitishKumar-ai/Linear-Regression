## Problem Statement

The current five-agent Discord experiment creates the appearance of a team but not genuine collaboration. Agents are either orchestrated as isolated workers whose outputs a human must combine, or they receive the same raw chat history and gradually collapse into the same voice, assumptions, and behavior.

The internal InModel workspace needs agents that behave like governed employees: persistent identities, bounded private memory, explicit access to tools and data, structured peer collaboration, visible work status, and human approval before execution or public action.

## Demand Evidence

The first user is the builder operating the InModel workspace. The concrete pain is stated directly:

- "I am struggling to get a proper voice or collaboration experience."
- "They do not collaborate, they just orchestrate."
- In the Discord role experiment, agents sharing the same chat begin to "talk in same manner."

This is observed pain in an active prototype, not hypothetical market demand. External demand and willingness to pay are untested; this design intentionally starts as an internal system.

## Status Quo

- Five identities exist: Rhea, Vic, Nadia, Tobi, and Emre.
- Discord roles give them visible names and channels, but do not enforce identity or memory boundaries.
- The human manually coordinates models and combines their outputs.
- Local JSON tracks calendars, work logs, and clients.
- Tasks Tracker and Document Hub in Notion are connected and live synchronization is verified.
- There is no durable panel run, typed collaboration protocol, private memory store, approval state machine, policy engine, or Discord conversation runtime.

## Target User & Narrowest Wedge

Target user: the owner/operator of the internal InModel agent organization.

Narrowest wedge: one reliable `/panel plan <feature>` workflow that produces a better reviewed plan than a single agent, records the work in Notion, and cannot execute before human approval.

Individual invocation through `/Rhea <request>` is a future adapter workflow. It is not implemented or accepted in version one; the first implementation and evaluation center exclusively on `/panel plan`.

## Constraints

- Internal InModel workspace first; no multi-tenant customer platform.
- Five fixed agent identities from `config/agents.json`.
- Discord is the conversational interface, not the source of runtime truth.
- Notion is the visible work ledger, not the runtime brain.
- Agent private reasoning and private memory are never copied into shared chat or Notion.
- Collaboration uses typed artifacts rather than one shared raw transcript.
- Panel membership and collaboration depth are adaptive; Rhea records why specialists are included or omitted.
- Plan approval and external-action approval are separate gates.
- LinkedIn, InModel publishing, production deployment, external messaging, spending, and access grants remain disabled in the first vertical slice.
- Version one ends after plan approval in user-facing behavior. A deterministic local mock records an execution result only in automated acceptance tests; it performs no CLI, network, file, or external mutation.

## Premises

1. `/panel` is a controlled work cycle, not an unrestricted group chat.
2. Identity and access boundaries must be enforced by runtime data and policy, not only prompts or Discord roles.
3. Notion stores visible company work state; the controller stores live runs, private memory, permissions, budgets, and audit history.
4. Approval to execute internal work never implies approval to publish or perform another external action.
5. Adaptive participation is better than forcing all five agents to independently answer every request. This remains an empirical bet and must be evaluated.

## Cross-Model Perspective

An independent cold review described the strongest version as a governed collaboration runtime, not another chatbot swarm. Its key insight was: "Agents exchange typed artifacts, not private reasoning." The durable product is the artifact-and-state protocol; Discord, Notion, and specific model providers are adapters.

The reviewer challenged mandatory independent proposals. Similar models can produce correlated answers, performative disagreement, latency, and token cost. The design therefore uses adaptive participation and records selection reasons. A later A/B evaluation should compare adaptive/sequential review with blind independent proposals.

The suggested prototype uses TypeScript, Discord.js, SQLite, Drizzle, Zod, one model provider, the existing Notion integration, one local controller, deterministic phases, append-only audit events, approval buttons, and one harmless sandbox tool.

## Approaches Considered

### Approach A: Discord-first prototype

Extend the current project directly through Discord handlers. This ships the visible experience fastest but risks coupling durable organization logic to Discord events, messages, and interaction lifecycles.

### Approach B: Controller core with adapters

Create a channel-independent controller for identities, panel runs, typed artifacts, memory boundaries, permissions, approvals, tool policy, and audit events. Discord and Notion become adapters. This is the selected approach because it preserves the product boundary while still shipping one narrow workflow.

### Approach C: Workflow framework integration

Use LangGraph, AutoGen, or an agent SDK as the main runtime. These provide persistence, handoffs, and interrupts, but may impose orchestration abstractions on the differentiated collaboration protocol. Revisit after the protocol is proven and framework requirements are concrete.

## Recommended Approach

### System boundary

```text
Discord adapter ───────┐
Notion adapter ────────┤
CLI/workspace adapter ─┼──> Company Controller ──> Model provider
Calendar adapter ──────┤          │
Publishing adapters ───┘          ├── SQLite runtime state
                                  ├── private memory namespaces
                                  ├── policy and approval engine
                                  └── append-only audit events
```

The controller accepts commands, chooses agents, advances deterministic run phases, validates artifacts, builds agent-specific context, requests approvals, invokes permitted tools, and emits events. Adapters translate external systems into controller commands and render controller events; adapters do not own workflow decisions.

### First workflow

`/panel plan <feature>` creates a durable panel run:

1. **Intake**: store requester, goal, project, Discord location, and idempotency key.
2. **Clarify**: Rhea asks up to three outcome-focused questions when required.
3. **Select**: Rhea selects relevant specialists and records a reason for every included or omitted agent.
4. **Propose**: selected agents create role-specific proposals. Blind independence is optional, chosen by the collaboration policy.
5. **Challenge**: each participant must question, object to, or materially improve at least one artifact from another agent.
6. **Revise**: affected agents revise once and cite the artifact IDs that changed their work.
7. **Consolidate**: Rhea produces one recommendation, alternatives, unresolved risks, proposed assignments, and verification criteria.
8. **Approval**: the run pauses durably. Discord shows `Approve plan`, `Request revision`, and `Cancel`.
9. **Close**: project the approved plan and collaboration summary to Notion. Version-one user runs stop here.

Automated acceptance tests exercise approval gating through a test adapter that attempts a no-capability deterministic action. Mock execution is not represented by production domain states.

### Run states

```text
DRAFT -> CLARIFYING -> SELECTING -> PROPOSING -> CHALLENGING
      -> REVISING -> AWAITING_PLAN_APPROVAL -> COMPLETED

Any active state -> FAILED | CANCELED
AWAITING_PLAN_APPROVAL -> REVISION_REQUESTED -> REVISING
AWAITING_PLAN_APPROVAL -> APPROVAL_INVALIDATED -> AWAITING_PLAN_APPROVAL
AWAITING_PLAN_APPROVAL -> COMPLETED_SYNC_PENDING -> COMPLETED
```

Transitions are allowlisted. Clarification may complete with zero questions, but still enters and exits `CLARIFYING` so the audit trail is uniform. Every transition writes an audit event in the same transaction.

Phase guards:

- `CLARIFYING -> SELECTING`: Rhea submitted zero to three questions and each submitted question has an answer.
- `SELECTING -> PROPOSING`: Rhea plus at least one specialist are selected; one routing rationale explains the chosen set.
- `PROPOSING -> CHALLENGING`: every selected specialist has one valid proposal, or is marked timed out after one retry and removed while at least one specialist remains.
- `CHALLENGING -> REVISING`: at least one `question` or `objection` from an agent other than the consolidator references a proposal. `challenge` is shorthand for the union of those two artifact types. One independent challenge per plan is required; additional challenges are optional.
- `REVISING -> AWAITING_PLAN_APPROVAL`: challenged proposals have either one revision or an explicit `revision_declined` artifact; Rhea submits a valid consolidated plan.
- `AWAITING_PLAN_APPROVAL -> COMPLETED`: an authorized human approves the current plan version and the outbound Notion projection succeeds.
- `AWAITING_PLAN_APPROVAL -> COMPLETED_SYNC_PENDING`: approval succeeds but the Notion projection is durably queued; delivery later advances to `COMPLETED`.
- Any phase with no remaining specialist, invalid artifacts after one correction, or exhausted provider retry budget transitions to `FAILED` with an operator-visible blocker.

The controller promises at-least-once adapter delivery, not exactly once. A transactional outbox stores Discord/Notion delivery intents. Adapters use stable idempotency keys and reconcile remote identifiers; duplicates remain possible when a provider offers no deduplication and must be detected by origin/run IDs.

### Typed collaboration artifacts

Every artifact contains `id`, `run_id`, `author_type` (`agent`, `human`, or `system`), `author_id`, `type`, `created_at`, `visibility`, `references`, and a validated type-specific payload.

Initial types:

- `clarifying_question`
- `specialist_proposal`
- `evidence`
- `question`
- `objection`
- `revision`
- `revision_declined`
- `selection_decision`
- `consolidated_plan`
- `approval_request`
- `approval_decision`
- `execution_result`
- `verification_result`
- `blocker`
- `work_summary`

Visibility values are `agent_private`, `panel`, `company`, and `human_only`. Version-one agent proposals, evidence, questions, objections, revisions, selection decisions, and consolidated plans use `panel`. Human approval requests/decisions and operator blockers use `human_only` plus a separately rendered safe status in Discord. Private context never becomes an artifact automatically.

Reference edges are typed as `derives_from`, `evidence_for`, `challenges`, `answers`, `revises`, and `supersedes`. An objection must `challenge` a proposal or evidence artifact. A revision must `revise` a proposal and reference the challenge, question, or evidence that caused it. A consolidated plan must `derive_from` its source artifacts. Factual claims require an `evidence_for` edge; labeling unsupported content as synthesis is not sufficient.

Every artifact payload has a Zod schema with `schema_version: 1`. Updates create a new artifact with `supersedes`; artifacts are append-only. Version one retains artifacts and audits indefinitely in the local database and provides no deletion UI. A later retention policy must preserve audit tombstones.

Minimum payload contracts:

- proposal: `problem`, `recommendation`, `assumptions[]`, `risks[]`, `evidence_refs[]`;
- evidence: `claim`, `source_type` (`tool`, `document`, `observation`, or `agent_analysis`), `source_uri?`, `excerpt?`, `collected_at`; only tool, document, and human observation may substantiate external factual claims, while agent analysis is reasoning that must derive from other evidence;
- question: `target_artifact_id`, `kind` (`clarification`, `assumption`, or `evidence_gap`), `question`, `requested_answer_shape`;
- objection: `target_artifact_id`, `kind` (`feasibility`, `security`, `scope`, `evidence`, or `user_value`), `claim`, `requested_change`;
- revision: `target_artifact_id`, `change_summary`, `response`, `retained_risks[]`;
- revision declined: `target_artifact_id`, `challenge_artifact_id`, `reason`, `retained_risk` and must reference both with `answers`;
- selection decision: `selected_agent_ids[]`, `routing_rationale`, `collaboration_mode` (`sequential` or `blind_then_reveal`);
- clarifying question: `question`, `why_needed`; its human answer is an `evidence` artifact with `source_type: observation` and an `answers` edge;
- consolidated plan: `goal`, `recommended_steps[]`, `alternatives[]`, `unresolved_risks[]`, `assignments[]`, `verification_criteria[]`, `source_refs[]`; assignment is `{agent_id, outcome, dependencies[], done_when[]}` and verification criterion is `{id, statement, evidence_required}`;
- approval request: `plan_artifact_id`, `plan_version`, `content_hash`, `expires_at`;
- approval decision: `request_artifact_id`, `decision` (`approved`, `rejected`, `revision_requested`, or `revoked`), `approver_id`, `decided_at`, `change_request?`;
- blocker: `phase`, `code`, `summary`, `retryable`, `operator_action?`;
- work summary: `decision`, `completed[]`, `not_completed[]`, `blockers[]`, `evidence_refs[]`, `contributors[]`.

`Request revision` requires `change_request` with `target` (`consolidated_plan` or source artifact ID), `requested_change`, and `acceptance_condition`. It creates a new human-authored `question` referencing the target, increments the consolidated plan version after revision, and returns through `REVISION_REQUESTED -> REVISING`. Source proposals change only when explicitly targeted; Rhea always issues a new consolidated plan artifact that supersedes the prior plan.

### Identity and memory

The long-term agent profile has the following fields. Version one implements only identity, charter, model configuration, project scope, and artifact visibility. Durable memory, working hours, budgets, and capability grants are interface placeholders with no version-one tables or enforcement:

- immutable identity ID and display identity;
- role charter, responsibilities, and communication style;
- allowed model configuration;
- private durable memory namespace;
- project/workspace scopes;
- allowed tools and operations;
- working-hour, concurrency, token, and cost limits;
- approval rules.

Context assembly is explicit:

```text
role charter
+ current assigned goal
+ selected private memories for this agent
+ approved shared company facts
+ referenced collaboration artifacts
+ tool policy for this run
```

Raw private chain-of-thought is neither requested nor stored. Agents see only artifacts authorized by visibility and project scope. Shared company memory accepts only approved decisions, facts, summaries, and evidence.

Version one does not implement durable semantic/vector memory and does not create a `memory_entries` table. Private context consists of the agent charter plus artifacts authored by or explicitly addressed to that agent in the current run, capped by recency and a configured token limit. Every retrieval query includes `agent_id`, `project_id`, and allowed visibility; authorization is checked before ranking. Memory promotion is deferred. This narrows the enforceable privacy guarantee to preventing unauthorized storage and context retrieval. Output redaction and adversarial leak tests reduce, but cannot prove absence of semantic leakage from model-generated text.

### Adaptive panel policy

Rhea begins with role routing rules:

- product/user uncertainty -> Nadia;
- architecture, reliability, or permissions -> Vic;
- implementation/code -> Emre;
- execution, testing, remote operations, or rollout -> Tobi;
- cross-functional synthesis and accountability -> Rhea.

The selection artifact records selected agent IDs, one routing rationale, and `collaboration_mode`. Recording a separate omission reason for every fixed agent is deferred unless evaluation shows it is useful. The controller requires Rhea plus at least one specialist and requires a challenger distinct from Rhea before consolidation.

### Approval and policy model

Future approval classes are distinct but only `PLAN_EXECUTION` is modeled in version one:

- `PLAN_EXECUTION`: permits only the exact approved internal plan version.
- `EXTERNAL_PUBLICATION`: required for each LinkedIn or InModel publication.
- `PRODUCTION_CHANGE`: required for deploy, merge, or production configuration.
- `EXTERNAL_COMMUNICATION`: required for outbound messages outside approved internal channels.
- `FINANCIAL_ACTION`: required for any spend.
- `ACCESS_CHANGE`: required for credential, sharing, role, or permission changes.
- `DESTRUCTIVE_ACTION`: required for deletion or irreversible mutation.

Version-one approval policy:

- eligible approvers are stable Discord user IDs configured in the controller, never display names or roles alone;
- one affirmative decision from an eligible approver approves a plan;
- the first valid decision wins; later concurrent clicks return the stored result;
- an unanswered approval request expires after 24 hours; an approval decision is consumed immediately by the terminal transition and cannot expire afterward;
- an approver may revoke only before the terminal transition commits; afterward a new panel run is required;
- any canonical plan payload change creates a new version and invalidates the prior request;
- rejection or `Request revision` moves the run to `REVISION_REQUESTED`;
- approvals bind to the plan artifact ID, version, and a SHA-256 hash of canonical JSON.

Canonical JSON includes schema version and all decision-bearing payload fields with recursively sorted object keys and array order preserved. It excludes artifact IDs, timestamps, delivery metadata, and audit metadata. Changing the canonicalization version invalidates pending approvals.

Expiry, revocation, or payload change writes `APPROVAL_INVALIDATED`. For an unchanged plan after expiry, the controller creates a replacement request with the same plan version/hash and a new expiry. A changed plan always receives a new plan artifact, version, hash, and approval request.

A minute-level local scheduler invalidates expired pending requests. The same expiry check also runs during startup recovery and immediately before handling any approval interaction, so sleeping or restarted processes cannot accept stale requests.

### Discord experience

- `/Rhea <request>` is explicitly deferred until its persistence and authorization semantics are designed.
- `/panel plan <feature>` creates one panel thread.
- The thread renders phase changes and concise agent-authored artifacts in conversational form.
- It does not dump hidden prompts, private memory, or private reasoning.
- Approval buttons appear only when the controller state is `AWAITING_PLAN_APPROVAL`.
- Duplicate button presses are idempotent; unauthorized users receive a denial without changing state.
- The controller stores durable Discord channel and message IDs. On restart it edits the run card when possible; if the interaction token or message is unavailable, it posts one replacement linked by the same run ID and marks the previous delivery superseded.

### Notion mapping

Tasks Tracker remains the visible operational ledger. Add or map fields for:

- Task name
- Agent/owner
- Status
- Due date or blocked time
- Priority
- Description
- Panel run ID
- Current phase
- Blocker
- Approval status
- Evidence link
- Last controller update

Document Hub stores completed summaries:

- Doc name
- Category
- Summary
- Panel run ID
- Decision
- Work completed
- Work not completed
- Blockers
- Evidence links
- Contributors
- Approval record

Notion rows contain no secrets, private memory, raw prompts, or private reasoning. Version one is outbound-only from controller to Notion. Manual Notion edits do not change runtime state. Controller writes use a stable origin/run ID and reconcile remote page IDs before retrying.

Default status projection is `DRAFT..REVISING -> In progress`, `AWAITING_PLAN_APPROVAL -> Waiting`, `COMPLETED_SYNC_PENDING -> Waiting`, `COMPLETED -> Done`, `FAILED -> Blocked`, and `CANCELED -> Canceled`. If Notion lacks one of these options, the adapter writes the controller phase to `Current phase`, leaves the existing Status unchanged, and records `sync_needs_mapping` for the operator.

### Persistence model

SQLite tables for the first version:

- `agents`
- `agent_permissions`
- `panel_runs`
- `panel_participants`
- `artifacts`
- `artifact_references`
- `approval_requests`
- `approval_decisions`
- `tool_invocations`
- `audit_events`
- `adapter_deliveries`
- `outbox_events`

Use Drizzle migrations and Zod validation. One controller process owns writes; SQLite uses WAL mode, a five-second busy timeout, and database transactions. Each Discord event ID is consumed once through a uniqueness constraint. The controller has a random process UUID. It claims a run atomically with `UPDATE ... WHERE lease_expires_at < database_now OR lease_owner = self`, uses a 30-second lease, and renews every 10 seconds using SQLite's clock. Another process may recover only after database-time expiry. Encrypt secrets outside SQLite using environment variables or the OS secret store. Never persist provider tokens inside agent context or artifacts.

### Failure behavior

- Invalid artifact: reject, record validation error, allow one corrected submission.
- Model call: persist invocation intent before dispatch and result after response. Retry once on a confirmed pre-dispatch transport failure. A timeout after dispatch becomes `needs_operator` because completion is unknowable; the operator may explicitly retry while accepting duplicate-cost risk. Model calls have no external mutation.
- Confirmed pre-dispatch provider failure: retry once. Post-dispatch timeout after 60 seconds: never retry automatically; mark `needs_operator` because completion and billing are unknowable.
- Discord unavailable: keep the run durable; retry adapter delivery without rerunning agents.
- Notion unavailable: commit internal completion as `COMPLETED_SYNC_PENDING`, show that outcome in Discord, and retry idempotently. After dead-lettering, the run remains visibly sync-pending until the operator repairs mapping/access and retries.
- Process restart: resume from committed phase and pending deliveries.
- Approval expiry: return to `AWAITING_PLAN_APPROVAL` with the unchanged plan version/hash and a replacement request. Plan mutation: issue a new plan version/hash and new request.
- Dead-letter: after five adapter attempts with exponential backoff capped at 15 minutes, mark delivery `needs_operator`; a CLI command can inspect and retry it.
- No material challenge: `requested_change` may state that the proposal survives review, but it must identify what was checked and why no change is requested.

### Security boundary

- Deny by default for tools, paths, workspaces, and data scopes.
- Tool calls receive short-lived capability grants created for one run and operation.
- CLI execution is disabled. The acceptance-test mock is an in-process pure function with no capabilities.
- Logs redact credentials and sensitive arguments.
- Discord user and role authorization are checked by stable IDs, never display names.
- Agent-authored text is untrusted input and cannot grant itself permissions, alter system policy, or approve tool calls.

## Open Questions

1. Which model provider powers the first live run, and can it support all five identities economically?
2. Which Discord server, channel IDs, and human role IDs are authorized?
3. Should individual `/Rhea` conversations persist per channel, thread, project, or requester?
4. Do the target Notion databases support the default status mapping, or must the workspace mapping be overridden?
5. When should adaptive selection use blind independent proposals rather than sequential critique?

None of these questions blocks implementing the controller domain model and a mocked end-to-end panel test. Live provider evaluation waits until the provider, per-run token ceiling, and timeout budget are configured.

## Success Criteria

Run five representative internal feature-planning tasks and require:

- 100% of state transitions conform to the allowlisted state machine.
- The test adapter records zero action invocations before approval of the exact current plan hash.
- Zero unauthorized private-namespace reads in automated policy and cross-namespace tests; leak-oriented prompt tests produce no known seeded secrets in outbound artifacts.
- 100% of factual consolidated claims have evidence references; non-factual recommendations either derive from proposal artifacts or are explicitly labeled as Rhea's judgment.
- Every plan has at least one independent challenge from a non-consolidating agent.
- Every panel has one recorded rationale for its selected participants.
- A killed and restarted controller resumes every paused run; remote duplicates are detectable by run ID, reconciled automatically when possible, and marked superseded when replacement is required.
- At least three of five panels score at least two points higher than the stored Rhea-only baseline. For each task, first run Rhea alone with the same goal and clarification answers, store that artifact before panel exposure, then blind the human evaluator to source/order. Score completeness, risk discovery, actionability, and evidence from 0 (absent), 1 (partial), or 2 (strong), plus overall decision confidence from 0 to 2, for a 10-point total. Store rubric scores and comments with the run.
- Median time and token cost are recorded, creating a baseline for adaptive versus all-agent participation.

## Distribution Plan

Version one runs as one local Node/TypeScript service inside the InModel workspace and is started through an npm script. It is not packaged for external users.

Once the directory becomes a Git repository, add CI that runs schema checks, unit tests, migration tests, state-machine property tests, adapter contract tests, and a credential-free mocked panel flow. Deployment and long-running hosting remain separate scope until the local workflow passes the five-task evaluation.

## Dependencies

- Discord application credentials and stable server/channel/role IDs.
- One model provider credential and model choice.
- Existing Notion integration and connected Tasks Tracker/Document Hub.
- SQLite, Drizzle, Zod, Discord.js, and a test runner.
- One deterministic no-capability mock execution fixture for automated tests.
- Tightening inherited Notion access if the integration currently sees the Space HQ parent beyond the intended databases.

## Delivery Milestones

1. **Domain/mock acceptance:** SQLite schema, state machine, Zod artifacts, approval hashing, policy tests, restart recovery, deterministic agent/test adapters. No live Discord, Notion, or model calls. Passing this milestone does not mean version one is complete.
2. **Discord and Notion integration:** live `/panel plan`, durable thread rendering, authorized approval interaction, outbound Tasks Tracker/Document Hub projection, outbox reconciliation, and sync-pending recovery.
3. **Live provider evaluation:** configure one provider, rate/timeout/token ceilings, run the five-task blinded evaluation, and meet every Success Criterion. Version one is complete only after this milestone passes.
