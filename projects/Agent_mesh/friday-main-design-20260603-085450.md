## Problem Statement

AI tools today are brains without hands. They can think but cannot act without a human
clicking buttons. Inmodel ships agents with both: a persistent brain that learns, attached
to arms that can scan code, run campaigns, and keep working 24 hours a day without
supervision.

The founder has already built the Agent Mesh harness (durable 3-pass loop, EventBus,
StateStore, Orchestrator — lives in `harness/` in the Agent_mesh repo). The next step is
building the two product arms on top of that harness and validating that people will pay.

---

## Core Abstraction — The 3-Pass Loop

Every agent job runs three durable steps:
- **Pass 1 — Plan:** Cheap model (Flash-Lite) decomposes the task into steps
- **Pass 2 — Execute:** Stronger model (Sonnet 4.6) does the work
- **Pass 3 — Review:** Verifier model checks output quality and emits a verdict

Each pass is a DBOS `@step()` — if the process crashes mid-run, it resumes from the last
completed pass. No job is ever lost. The existing `harness/agents/base.py` implements this
loop; Inmodel agent classes override the three prompt methods only.

## Accepted Premises

1. **No fine-tuned model for CommitGuard MVP.** Sonnet 4.6 + Semgrep is sufficient to
   find real vulnerabilities customers will pay for today. Train Gemma 4 E4B after the
   first 10 paying customers.

2. **E2B replaces DIY Firecracker.** `pip install e2b` gives managed Firecracker microVMs
   with identical isolation. Building a Firecracker pool from scratch is multi-month infra.
   Migrate to self-hosted only when E2B costs exceed $200/month.

3. **One L4 cannot train and serve simultaneously.** Use Modal or HuggingFace AutoTrain
   (pay-per-run) for training. Dedicated L4 serving arrives after volume justifies it.

4. **`learning_loop.py` is Stage 2.** Deferred to post-MVP. First 20 real scans teach
   more than any automated training loop.

5. **Both arms built in parallel.** Marketing Agent reaches first revenue faster (zero
   training dependency, Typefully + Gmail MCPs live today). Two revenue channels in 4 weeks.

## E2B Sandbox Contract

`verifier.py` sends this to E2B and parses the response:

```python
# Repo context enters E2B via file upload before PoC execution:
sandbox = Sandbox(template="base")
sandbox.filesystem.write("/repo/target.py", target_file_content)  # relevant file only
result = sandbox.run_code(poc_code, timeout=30)  # 30s hard limit
# Full repo clone is NOT sent — verifier.py extracts the relevant file(s)
# from the local Semgrep scan results and uploads only those.

# Confirmation logic (in verifier.py):
# CONFIRMED    — exit code 0 AND stdout contains expected exploit marker
# UNVERIFIABLE — exit code != 0 OR timeout OR ambiguous stdout
# FALSE_POSITIVE — LLM review step determines no exploitable path exists

# E2B environment: read-only repo clone, no network egress, 2GB RAM, 2 CPU
```

PoC format: Python script that imports from the cloned repo and demonstrates the
vulnerability. CommitGuard's Sonnet 4.6 step generates the PoC; E2B executes it.

## scheduler.py Responsibilities

`scheduler.py` owns:
- Formatting content to platform character limits (X: 280 chars, LinkedIn: 3000)
- Calling Typefully MCP `typefully_create_draft` to create scheduled drafts
- Retry logic (max 3 attempts on Typefully API errors)
- Returning draft IDs for the report endpoint

`scheduler.py` delegates to Typefully MCP:
- Actual scheduling, publishing, analytics fetching
- OAuth / authentication (MCP handles it)

The verified-exploit step is Inmodel's moat. Snyk, GitHub GHAS, Semgrep do static

## Revised Build Order — Parallel Minimal (4 Weeks)

DBOS from Day 1 via inheritance. The existing `harness/agents/base.py` already uses
`@DBOS.step()` decorators. Inmodel agent classes (scanner.py, verifier.py, etc.)
extend `BaseAgent` and inherit that durability automatically — no changes needed.

`brain/orchestrator.py` (Week 4) is the higher-level DBOS `@workflow()` that chains
multiple agent runs into multi-step jobs (e.g., scan → verify → file as one durable
workflow). Individual agents run as durable steps from Day 1; the workflow chaining
layer arrives in Week 4. No refactor of agent code is required at Week 4.

```
WEEK 1 — BRAIN + COMMITGUARD SCAN
  Day 1:    inmodel/ repo scaffold (folder structure, pyproject.toml, .env.example)
  Day 2-3:  brain/llm_router.py (4 tiers, config-driven, zero hardcoded model names)
  Day 2-3:  brain/memory.py (Redis Streams publish/subscribe ONLY — pgvector deferred)
  Day 4-5:  agents/commitguard/scanner.py
              → Semgrep subprocess (JSON output parsing)
              → Sonnet 4.6 analysis of Semgrep hits
              → DBOS @step() wrapping from harness/agents/base.py
  Milestone: scanner.py runs on a public repo and returns raw Finding[] candidates

WEEK 2 — VERIFY + MARKETING FOUNDATION
  Day 6-7:  agents/commitguard/verifier.py (E2B sandbox, PoC generation, CONFIRMED verdict)
  Day 8-9:  agents/marketing/researcher.py (Gemini Flash-Lite web research)
  Day 9:    agents/marketing/content_writer.py (Sonnet 4.6 multi-platform content)
  Milestone A (Day 7): CommitGuard scan + verify end-to-end on one real CVE (no GitHub filing yet)
  Milestone B (Day 9): Marketing Agent generates 3 posts for a given goal (no publishing yet)

WEEK 3 — PLATFORM + FILE + PUBLISH
  Day 10-11: agents/commitguard/github_client.py (PyGithub, Issue template, rate limiting)
  Day 12-13: agents/marketing/scheduler.py (Typefully MCP wrapper, retry logic)
  Day 14-15: platform/api/app.py (inline routes for both arms, no separate route files)
  Milestone: POST /commitguard/scan files a real GitHub Issue on a real repo
             POST /marketing/campaign publishes a real post via Typefully MCP

WEEK 4 — OBSERVABILITY + DEPLOY + FIRST CUSTOMERS
  Day 16-17: brain/orchestrator.py (DBOS durable 3-pass, wraps harness/orchestrator.py)
             Langfuse span tagging in orchestrator.py (trace every step)
  Day 18-19: infra/setup_vm.sh + systemd services (4 services, see below)
             GCP e2-standard-4 deploy (FastAPI + Postgres + Redis + worker)
  Day 20:    Outreach — 10 developers for CommitGuard beta
             Outreach — 5 founders for Marketing Agent beta
  Milestone: 1 person has paid for CommitGuard
             1 person has paid for Marketing Agent (separate targets)
```

## VM Process Model (Week 4)

GCP e2-standard-4 (4 vCPU, 16 GB RAM). All managed by systemd `Restart=always`.

```
inmodel-api.service      → uvicorn platform/api/app.py (port 8000)
inmodel-worker.service   → DBOS orchestrator worker (polls job queue)
inmodel-postgres.service → Postgres 15 (port 5432)
inmodel-redis.service    → Redis 7 with AOF enabled (port 6379)
```

No Docker at MVP — systemd is simpler and more debuggable for a solo founder.
`infra/setup_vm.sh` bootstraps all four services from a fresh Ubuntu 22.04 instance.
CI/CD: `deploy.yml` GitHub Action (SSH + `git pull + systemctl restart`) on merge to main.
Langfuse runs in a separate Cloud Run container (free tier for < 50K events/month).

Before writing a single file in the `inmodel/` repo:

**CommitGuard:** Find one public GitHub repo with known security issues. Manually run

"I found a SQL injection in your repo. Want the full report with proof of exploit?"

**Marketing Agent:** Find one solo founder on X who hasn't posted in 2+ weeks. DM them:
"I can generate a week of posts for you — your voice, your product, ready to schedule.
Want me to do one for free so you can see?" If they say yes, do it manually in one hour.

If either response is "yes, send it" — you have demand. Build that arm first.
