# Design: Consolidate Conductor Features into Agent Mesh UI

## Problem Statement

AgentMesh currently has two frontends:

- `ui/` is the new Codex-style Agent Mesh operator console.
- `ui-next/` is the inherited Conductor UI with working integrations for workflow execution, definitions, tasks, queues, schedules, agents, health, and API tooling.

The split has produced duplicate routing, API clients, domain types, event handling, and page ownership. The goal is to make `ui/` the only product frontend while preserving the useful Conductor capabilities already implemented in `ui-next/`.

The immediate demo must work locally against `server-lite` and prove one complete operator loop:

1. Select and run an agent.
2. Receive live execution events.
3. Open the resulting Conductor workflow and inspect its tasks.
4. Pause, resume, or retry the workflow.
5. Engage and release the global cooperative execution halt.

## What Makes This Cool

The result is not a generic Conductor administration console with Agent Mesh pages attached. It is an Agent Mesh workspace where durable Conductor workflows are the execution substrate. A user starts with an agent goal and can immediately move from high-level intent to the exact workflow, task, event, and safety state underneath it without changing applications.

The demo moment is:

```text
Run agent
   |
   v
Live plan / execute / review events
   |
   v
Open durable workflow and inspect task state
   |
   +--> pause / resume / retry
   |
   +--> emergency stop all agents
```

## Constraints

- `ui/` remains visually and structurally canonical.
- `server-lite` is the canonical local backend.
- Canonical APIs are:
  - `/health`
  - `/api/agents/*`
  - `/api/workflow/*`
  - `/api/tasks/*`
  - `/api/metadata/*`
- The migration must not copy MUI components or the `ui-next` application shell into `ui/`.
- Existing unrelated changes in `ui-next` must be preserved until their behavior has been migrated and verified.
- The first milestone is a local demo, not public deployment.
- Tests should use real `server-lite` behavior where practical. Avoid duplicating backend behavior in mocks.

## Premises

1. `ui/` becomes the only frontend shipped as the AgentMesh product.
2. `server-lite` and the TypeScript runtime become the only backend contract used by `ui/`.
3. `ui-next` is a behavioral reference and temporary donor codebase, not a second application to maintain.
4. The first milestone is complete only when the full agent execution loop works.
5. Remaining Conductor capabilities migrate incrementally after the first loop is verified.
6. Legacy Python/FastAPI-shaped endpoints in `ui/src/lib/api.ts` are removed or isolated; they must not silently remain as the default path.

## Approaches Considered

### Approach A: Direct Feature Port

Copy the relevant API methods and recreate Agents, Workflows, Events, and Killswitch screens directly in `ui/`.

- Effort: Small
- Risk: Medium
- Advantage: Fastest visible demo.
- Cost: Preserves duplicate response types and endpoint assumptions.
- Completeness: 7/10

### Approach B: Contract-First Incremental Migration

Create a single typed `server-lite` client and normalized domain/event layer in `ui/`. Migrate one complete user flow at a time, verify it against the real backend, then remove the corresponding `ui-next` behavior.

- Effort: Medium
- Risk: Low
- Advantage: One backend contract, one event format, one ownership boundary.
- Cost: Requires a small foundation before all pages become functional.
- Completeness: 10/10

### Approach C: Embed or Link `ui-next`

Keep both applications and expose Conductor screens from `ui/` through links, an iframe, or a microfrontend boundary.

- Effort: Small initially
- Risk: High
- Advantage: Existing screens remain available immediately.
- Cost: Duplicate builds, routing, state, themes, and API clients remain indefinitely.
- Completeness: 5/10

## Recommended Approach

Use Approach B: contract-first incremental migration.

The migration boundary should be:

```text
React pages and components
          |
          v
UI domain services / hooks
          |
          v
server-lite typed API client
          |
          +-------------------+
          |                   |
          v                   v
 REST request adapters    SSE event adapter
          |                   |
          +---------+---------+
                    |
                    v
        Canonical UI domain models
                    |
                    v
         Agent Mesh page state
```

Pages must not know whether a backend payload originally came from an Express agent route or a NestJS Conductor route. The API layer owns that translation.

### Event Normalization

The TypeScript backend emits camelCase event fields:

```json
{
  "agentId": "commit_guard",
  "workflowId": "workflow-id",
  "eventType": "agent_step_completed",
  "payload": {},
  "timestamp": 1750300000000
}
```

`ui/src/lib/events.ts` currently expects legacy snake_case fields from `/stream`. Replace that legacy stream with `/api/agents/events` and normalize both camelCase and snake_case only during a short migration window. Remove the snake_case branch once legacy Python support is deleted.

SSE uses the browser's native `EventSource` reconnection behavior. The stream is
transient and non-replayable: after a reconnect, the UI refetches the active
workflow so durable workflow/task state remains authoritative.

```text
CONNECT
  |
  +--> open ----------> CONNECTED
  |
  +--> error ---------> RECONNECTING
                           |
                           +--> browser reconnects EventSource
                           |
                           +--> open -> CONNECTED
                                  |
                                  +--> refetch active workflow

manual close -> CLOSED, no reconnect
```

## Migration Plan

### Engineering Review Scope

The first implementation pass is limited to the core operational slice:

1. Run an agent through the canonical `server-lite` route.
2. Receive and display canonical SSE events.
3. Inspect the resulting workflow and its tasks.
4. Pause, resume, and retry the workflow.
5. Engage and release the global killswitch.

Schedules, definitions, queues, API documentation, human approval, and deleting
`ui-next` are deferred. They are not prerequisites for this milestone.

### Phase 0: Freeze Ownership

1. Document `ui/` as canonical and `ui-next/` as migration-only.
2. Stop adding product features to `ui-next`.
3. Track migrated Conductor capabilities in a checklist.
4. Keep unrelated existing `ui-next` work intact until explicitly superseded.

### Phase 1: Typed Contract Foundation

1. Add one isolated `serverLiteApi` client for the migrated operational surfaces.
2. Keep the existing legacy `api` object unchanged for pages outside this milestone.
3. Add `serverLiteTypes.ts` for canonical UI models. Validate raw agent,
   workflow, task, killswitch, and event payloads with Zod before normalization;
   raw schemas and payload types remain private to `serverLiteApi`.
4. Keep legacy models in `ui/src/lib/types.ts` until their pages are migrated;
   do not create hybrid models with both legacy and canonical field names.
5. Add consistent error parsing for `{ error }`, `{ message }`, NestJS
   `{ message }`, empty responses, and schema failures. Validation errors identify
   the endpoint but do not include the complete raw payload.
6. Replace `/stream` with the canonical `/api/agents/events` client for the
   migrated activity/session surfaces.
7. Do not introduce a query framework or a separate hook per endpoint in this
   pass. Add local hooks only where shared lifecycle behavior requires them.
8. Use one small discriminated async-state type (`idle`, `loading`, `success`,
   `error`) with a typed `ApiError`. Mutations track the pending action/entity
   separately so contradictory boolean combinations are impossible.

### Phase 2: First Complete Demo Slice

1. Agents page loads `GET /api/agents`.
2. Run dialog posts to `POST /api/agents/:agentId/run`. The route calls the
   already-wired `WorkflowExecutorOps.startWorkflow()` and returns its persisted
   workflow ID; it must never return the worker adapter's placeholder value.
3. `App` owns one `activeWorkflowId`. Agent runs and workflow selections update it
   through callbacks; Session, Workflows, Activity, and workflow detail receive it
   as props. `App` synchronizes it with `?workflow=<id>` using the browser
   History API so refresh, back/forward, and shared links reopen the inspector
   without introducing a routing framework in this milestone.
4. SSE events are filtered by workflow ID and rendered in the transcript/activity feed.
5. Workflow detail loads from `GET /api/workflow/:workflowId`.
6. Tasks load from the workflow response or `/tasks` endpoint.
7. The returned active workflow opens directly by ID in a right-side inspector
   containing workflow status,
   tasks, matching events, and pause/resume/retry actions. On narrow screens the
   inspector becomes a full-screen sheet.
8. `WorkflowService` delegates pause, resume, retry, and terminate operations to
   `WorkflowExecutor` when it is wired, preserving the executor's status
   validation, locking, queue updates, and lifecycle notifications. A validated
   DAO fallback exists only for configurations without an executor.
   The inspector mirrors the lifecycle rules to disable known-invalid actions,
   while backend errors remain authoritative for stale or concurrent requests.
9. Workflow lifecycle failures use typed domain errors. Controllers map missing
   workflows to `404`, invalid transitions to `409`, and malformed requests to
   `400`, with one consistent error body for the typed UI client.
10. Workflow actions expose confirmation and visible pending/error states.
11. Global killswitch controls use `/api/agents/killswitch/*`. UI copy states
    that engagement blocks new runs and stops active agents at their next safety
    checkpoint; it does not promise instant interruption of in-flight tool or
    model calls.
12. Starting an agent while the killswitch is engaged shows the backend’s `503` reason.

### Phase 3: Conductor Operations

Migrate in this order:

1. Workflow search and workflow detail.
2. Task detail and logs.
3. Human approval.
4. Agent schedules.
5. Workflow and task definitions.
6. Queue monitor.
7. API documentation link.

Each capability is reimplemented with the Agent Mesh visual system. Do not copy MUI layout code.

### Phase 4: Retire `ui-next`

1. Verify every retained capability has an equivalent route in `ui/`.
2. Remove `ui-next` from local launch configuration and documentation.
3. Remove `ui-next` from build and Docker paths.
4. Delete the package only after build, integration tests, and the local demo pass without it.

## Interaction States

Every migrated flow must define:

- Loading state.
- Empty state.
- Backend unavailable state.
- Validation failure.
- `404` missing agent/workflow/task.
- `409` or invalid state transition where applicable.
- `503` killswitch engaged.
- SSE disconnected and reconnecting.
- Mutation pending state that prevents double submission.
- Success confirmation with a direct link to the affected workflow.

## Failure Modes

| Failure | Handling | User result |
|---|---|---|
| `server-lite` is offline | Typed network error and retry action | Clear “Backend unavailable” state |
| Agent ID no longer exists | Surface `404` from run endpoint | Return to refreshed agent list |
| Killswitch engages between page load and run | Surface `503` and refresh killswitch state | Run dialog remains recoverable |
| SSE disconnects | Native reconnect with visible state; refetch active workflow on reopen | Existing events remain visible and durable state is reconciled |
| Duplicate run click | Disable submit while request is pending | One workflow is created |
| Killswitch engaged during active work | Cooperative checks halt the agent at the next checkpoint | UI shows that shutdown may not be instantaneous |
| Event arrives before workflow detail fetch completes | Buffer by workflow ID | Timeline fills without losing events |
| Workflow action is invalid for current status | Disable known-invalid controls and surface backend rejection | User sees exact reason |
| Workflow search returns malformed or incomplete record | Adapter rejects or applies explicit optional defaults | Page shows a recoverable data error |
| User changes page during mutation | Abort when supported or ignore stale completion | No set-state-after-unmount behavior |

### Required Architecture

```text
UI recovery workspace
        |
        v
Topology-neutral Operator API client
        |
        v
Validated controller/router
        |
        v
OperatorStartAuthority
  - bounded request validation
  - idempotency receipt

  - per-workflow/start-key lock
  - synchronous persistence result
        |
        v
WorkflowExecutor interface
        |
        +--> SQLite implementation (local proof)
        +--> future distributed implementation

Lifecycle mutations
  -> typed command
  -> per-workflow lock
  -> load + validate transition
  -> mutate workflow and queues
  -> durable audit receipt
  -> publish bounded event
```

The HTTP route, scheduler, and any future trigger must call the same start authority. No adapter may acknowledge a workflow before durable creation succeeds.

### Engineering Findings and Corrections

1. **P0: Fix router composition.** Replace process-global `AppModule.agentRouter` state with an instance-scoped provider or middleware factory. Prove the mounted route with a real HTTP contract test.
2. **P0: Establish one start authority.** Validate trimmed, bounded input; require an idempotency key; perform the halt check under the same synchronization boundary as creation; return only after persistence succeeds.
3. **P0: Enforce local-only exposure.** Default to `127.0.0.1`, exact local UI origins, and fail closed when a non-loopback host is configured without an explicit unsafe-development override.
4. **P0: Implement typed domain failures.** `WorkflowNotFoundError`, `InvalidWorkflowTransitionError`, `SystemHaltedError`, `ValidationError`, and `IdempotencyConflictError` map centrally to stable `{ code, message, requestId }` responses.
5. **P0: Replace no-op locking.** Provide an interface-backed local per-workflow mutex and hold it across validation, mutation, queue changes, and publication.
6. **P1: Move the complete operator slice to one client.** Session, Agents, Workflows, inspector, events, and cooperative halt cannot mix legacy and canonical routes.
7. **P1: Make SSE recoverable.** Validate events, filter before retention, cap client/server buffers, emit heartbeat comments, and refetch workflow/task state after reconnect.
8. **P1: Bound and redact workflow evidence.** Paginate task detail, truncate large payloads, redact configured fields, and require explicit reveal for sensitive output.
9. **P1: Correct shutdown order.** Stop intake, schedules, worker polling, sweeper, and listeners; await completion; close HTTP; destroy persistence last.
10. **P1: Replace the smoke test with a recovery proof.** The test must inject a recoverable failure after one protected side effect, retry safely, and assert the final artifact and exactly-once side effect.
