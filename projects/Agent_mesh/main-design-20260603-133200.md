## Problem Statement

For this hackathon, we need a 3-minute live demo that generates a visceral "whoa" moment. The previous plan was to build a dual-arm "Inmodel Platform" (CommitGuard + Marketing Agent). But building both dilutes the hacker narrative and increases the risk of a live demo failure. We need to pivot strictly to the most impressive feature: an autonomous agent that not only finds a vulnerability using Semgrep but actively exploits it live in an E2B sandbox to prove it's real.

---

## Core Abstraction

The core abstraction is the DBOS 3-pass loop, already built in `harness/`:
- **Pass 1 — Plan:** Gemini Flash-Lite analyzes the repository structure.
- **Pass 2 — Execute (Scan):** Semgrep runs statically to find potential vulnerabilities.
- **Pass 3 — Execute (Exploit):** Sonnet 4.6 generates a Python Proof-of-Concept exploit.
- **Pass 4 — Verify:** The PoC is executed live inside an E2B sandbox microVM.

This simple, deterministic pipeline guarantees reliability for a live demo while preserving the magic of an AI autonomously hacking code.

---

## The "Whoa" Moment

The entire UI and narrative is structured around the execution of the exploit. We will build a Web Dashboard with Real-time Logs. The left pane shows the agent state (the DBOS loop), while the right pane shows a live, high-tension terminal view streaming stdout from the E2B sandbox. When the green text appears saying the exploit succeeded, the audience has their "whoa" moment.

---

## Target Users

**Hackathon Judges & Technical Audience:** They are skeptical of static analysis scanners (too much noise, mostly theoretical risks). They need to see a real exploit executing live to believe the tool is actually valuable.

---

## Accepted Premises

1. **The 'Whoa' Moment is binary:** The demo succeeds only if the live exploit actually executes and proves a vulnerability in a sandbox; just showing a static analysis report is a failure.
2. **Minimalist Agent Architecture:** We do not need a complex ReAct or autonomous agent loop; the existing DBOS 3-pass loop (Plan -> Execute -> Review) is strictly sufficient to generate and verify the PoC.
3. **Marketing Agent is a distraction:** Building both CommitGuard and Marketing Agent for a hackathon splits focus and dilutes the "hacker AI" narrative. We cut the Marketing Agent entirely for this weekend and focus solely on CommitGuard.

---

## Chosen Approach — Ideal Architecture (Web Dashboard with Real-time Logs)

A FastAPI backend using the DBOS orchestrator, with a simple React/Tailwind frontend (or vanilla HTML/JS for speed). The user enters a GitHub URL, and the UI shows a real-time terminal window streaming the E2B sandbox logs as the exploit runs. This is highly professional, visual, and sets up the exact architecture needed for the post-hackathon startup phase.

## API Contracts

### CommitGuard Live API

```
POST /api/scan
  Request:  { "repo_url": "https://github.com/owner/vulnerable-repo" }
  Response: { "job_id": "cg_hack123" }

GET /api/stream/{job_id}
  Response: Server-Sent Events (SSE) streaming logs directly from the DBOS loop and E2B sandbox.
  Format: 
    data: {"type": "state", "step": "Plan", "message": "Analyzing repo structure..."}
    data: {"type": "terminal", "output": "> Initializing E2B microVM..."}
```

## The Assignment

Before writing the backend, manually execute the flow to ensure it's possible in 3 minutes. Run Semgrep locally on a known vulnerable repo, copy the finding to Sonnet 4.6, ask it to write an exploit, and run that exploit manually against a local clone. If this takes longer than 3 minutes to execute manually, we must rethink the demo constraints (e.g., pre-caching the repo clone).
