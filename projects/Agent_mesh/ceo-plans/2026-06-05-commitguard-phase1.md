## Vision

### 10x Check
CommitGuard is not a scanner — it is a security engineer who never sleeps. The 10x version runs automatically on every PR via GitHub App, generates working PoC exploits that prove each finding is real (not a static analysis false positive), files detailed GitHub issues with AI-generated code patches, tracks the full vulnerability lifecycle from detection to verified remediation, and sends weekly security posture digests. A developer pushing at 2am gets a Slack notification: "HIGH — SQL Injection in src/db.py:47. CONFIRMED. Suggested fix: [3-line diff]."

### Platonic Ideal
The moment a CommitGuard finding lands, the developer thinks: "How did I ship this for 3 months without catching it?" The issue is not a static analysis report. It is proof — a working exploit that ran in a Firecracker sandbox. It comes with a concrete fix suggestion. It fires a Slack alert. Every finding is something a developer can act on immediately without leaving GitHub.

## What "CONFIRMED" Actually Means (per vuln category)

This is the most important definition in the plan. CONFIRMED is not "the LLM thinks this is real." It means the PoC script exited 0 AND the expected exploit marker appeared in stdout. Per category:

| Category | CONFIRMED definition | E2B PoC approach |
|---|---|---|
| SQL injection (string concat) | PoC constructs injection string, asserts it contains `'` or `OR 1=1`, prints `EXPLOIT_MARKER` | Self-contained script, no DB required |
| Hardcoded secrets | PoC loads the file, extracts the secret value, verifies it matches a known pattern (e.g., `sk-...`), prints `EXPLOIT_MARKER` | File-only, no network |
| Path traversal (pure file ops) | PoC calls the function with `../../etc/passwd`, verifies the resolved path escapes the root, prints `EXPLOIT_MARKER` | Self-contained |
| Insecure deserialization | PoC passes crafted payload to the deserialization function, verifies code execution via marker in stdout | Self-contained |
| Everything else (XSS, SSRF, auth bypass) | Returns UNVERIFIABLE — requires live server, database, or network | Not attempted in Phase 1 |

All PoC scripts are self-contained: they inline or mock the vulnerable function rather than importing from the repo. This avoids E2B import dependency failures. E2B receives only the PoC script, not the cloned repo.

### Data Models (Pydantic, JSON-serializable for DBOS)

```python
class Finding(BaseModel):
    id: str                      # UUID
    file: str
    line: int
    vuln_type: str               # e.g. "sql_injection"
    category: str                # one of PoC-executable categories or "unverifiable"
    description: str
    severity: str                # HIGH / MEDIUM / LOW

class VerifiedFinding(BaseModel):
    finding: Finding
    verdict: str                 # CONFIRMED / UNVERIFIABLE / FALSE_POSITIVE
    poc_summary: str
    cvss: str | None             # e.g. "8.1 HIGH" — AI-estimated
    cwe: str | None              # e.g. "CWE-89"
    webhook_fired: bool

class FiledFinding(BaseModel):
    verified_finding: VerifiedFinding
    fix_suggestion: str | None   # generated in github_client.py, stored here
    github_issue_url: str | None # null if filing failed or no write access
    issue_filed: bool
```

### CommitGuardWorkflow (main.py)

```python
@DBOS.workflow()
def commitguard_workflow(job_id: str, repo_url: str, max_files: int = 5):
    # DBOS replays steps on restart using cached return values.
    # Cached tmpdir path may not exist after a crash — clone_repo must be idempotent.
    # Strategy: use job_id as the tmpdir key: /tmp/commitguard-{job_id}/
    # On replay, if tmpdir exists, skip re-clone; if it doesn't, re-clone.
    tmpdir = clone_repo(job_id, repo_url)           # @DBOS.step
    raw_findings = scan(tmpdir, max_files)           # @DBOS.step → list[dict]
    filed = []
    for f in raw_findings:
        vf = verify(f, job_id)                       # @DBOS.step → dict (VerifiedFinding)
        if vf["verdict"] == "CONFIRMED":
            ff = file_issue(vf)                      # @DBOS.step → dict (FiledFinding)
            filed.append(ff)
        else:
            filed.append({"verified_finding": vf, "fix_suggestion": None,
                          "github_issue_url": None, "issue_filed": False})
    cleanup(job_id)                                  # @DBOS.step — rm /tmp/commitguard-{job_id}
    save_results(job_id, filed)                      # @DBOS.transaction
```

GET /api/commitguard/stream/{job_id}
  Auth: validates job_id belongs to the authenticated session's github_login

  Response: EventSourceResponse — SSE events shaped:

    { "event": "complete", "data": { "job_id": str } }

GET /api/commitguard/findings/{job_id}
  Response: {
    "job_id": str, "repo_url": str, "scan_duration_s": int,
    "total_semgrep_hits": int, "findings_truncated": bool,

        "id": str, "file": str, "line": int, "severity": str,

## GitHub Issue Filing — Target Repo Access

**Critical UX decision:** The OAuth token belongs to the user who initiates the scan. If they scan a repo they don't own (e.g., a dependency), they cannot file issues there.

**Phase 1 strategy:** File issues on the scanned repo if the token has write access. If not (GithubException: 403), log the failure, mark `issue_filed: false`, and include the full finding in the API response instead. The UI shows a "Copy to clipboard" button so the developer can file manually.

This is the right tradeoff for Phase 1: filing on owned repos works for the primary use case (scanning your own code). A CommitGuard bot account (with repo collaborator access) is a Phase 2 improvement.

## Notification Webhook

Single generic webhook format (works with Slack, Discord, Teams, any HTTP endpoint):

```json
{
  "text": "🔴 CommitGuard CONFIRMED: HIGH SQL Injection in src/db.py:47",
  "finding_id": "uuid",
  "verdict": "CONFIRMED",
  "severity": "HIGH",
  "file": "src/db.py",
  "line": 47,
  "github_issue_url": "https://github.com/owner/repo/issues/42"
}
```

Configured via `COMMITGUARD_WEBHOOK_URL` in `.env`. Fires in `verifier.py` immediately after CONFIRMED verdict (before the step returns). Langfuse span covers the verification; webhook is a side effect logged separately.

## Security Constraints (MANDATORY)

- `repo_url` MUST be validated before any use: `assert repo_url.startswith("https://github.com/")` — reject with 400 if not. This prevents SSRF via git clone and restricts scanning to GitHub only.
- `clone_repo()` MUST use list-form subprocess: `subprocess.run(["git", "clone", "--depth=1", repo_url, tmpdir], capture_output=True)` — NEVER `shell=True` with string interpolation.
- E2B PoC scripts are LLM-generated and run in an isolated Firecracker VM with no network egress — this is intentional. The LLM-generated code never runs on the host.
- GitHub token is stored encrypted (Fernet) in SQLite — existing protection from `github_integration.py`.

## Key Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Semgrep not installed | HIGH | Add `semgrep` to requirements.txt; document install in README |
| E2B API key missing | HIGH | Mock: return UNVERIFIABLE for all findings; CommitGuard runs as static scanner only |
| LLM-generated CVSS inconsistent | MEDIUM | "AI-estimated, not validated" disclaimer on all CVSS outputs |
| CONFIRMED verdict too permissive | HIGH | Define per-category exploit markers precisely (see CONFIRMED table above) |
| GitHub token missing repo scope | MEDIUM | Preflight scope check at scan submission; clear 403 error |
| No write access to target repo | MEDIUM | Issue filing fails gracefully; finding returned in API for manual copy |
| E2B concurrency exhaustion | MEDIUM | Serialize Phase 1 (max 1 scan at a time); 429 on concurrent request |
| DBOS tmpdir lost on crash | MEDIUM | Use job_id-keyed tmpdir; idempotent clone_repo step |
| Langfuse credentials missing | LOW | No-op fallback: skip @observe if LANGFUSE_PUBLIC_KEY not set |
| ETA underestimate | MEDIUM | State "2-10 min depending on finding count" in UI; never promise <2 min |
