## Baseline Architecture
- The CLI itself is built in Python (3.11+) using `typer`.
- The scaffolded project is a Python DBOS project using `pip` and a `requirements.txt`. It includes a `docker-compose.yml` for Postgres.
- The 3-pass loop is implemented as a single DBOS workflow orchestrating 3 DBOS steps (Plan, Execute, Review). State is explicitly saved to a lightweight domain-level `agent_runs` table linked to DBOS `workflow_id`.
- Pre-flight checks: The `agent-mesh init` subcommand and `make demo` script verify Docker is running, port 5432 is available, and an `OPENAI_API_KEY` is present. If the API key is missing, it interactively prompts the user for it. If any other check fails, it exits with a structured error (Problem + Cause + Fix + Docs format).

## Vision

### 10x Check
Imagine a CLI that scaffolds the first truly fault-tolerant, ACID-compliant multi-agent framework. Instead of single scripts, it provisions a true "Agent Mesh" — two communicating agents (e.g., a Researcher and a Coder) natively orchestrated via DBOS workflows. We drop the brittle local Streamlit observability and rely entirely on existing DBOS distributed tracing tools and established platforms (like LangGraph Studio/Langfuse) that read standard OTEL traces.

### Platonic Ideal
The user runs `agent-mesh init`, opens their editor, and sees a multi-agent orchestrated pattern out of the box. They run `make demo` and watch two agents safely coordinate a task without crashing, naturally persisting state through DBOS's internal tables.

- A `.cursorrules` or `CLAUDE.md` file tailored for DBOS multi-agent structures.

- **Code Execution Sandbox**: Executable code generated by the Coder must run in a restricted Docker container sandbox, preventing local host RCE.
