## Affected Pages/Routes
- `/attendance` — the marking screen; core of the offline write path. Test marking, saving, offline queue, reconnect sync, and the read-failure guard.
- `POST /api/attendance` — batch mark write; test markedAt skew clamp and idempotent replay.
- `GET /api/attendance?className=&date=` — the `existing` read; must surface errors, not return empty.
- `metrics:weekly` (script, not a route) — per-teacher × weekday matrix + ≥60%/≥4-days threshold.

## Key Interactions to Verify
- Mark a full class, save online → all marks land (existing happy path).
- Mark a full class OFFLINE → marks queue locally, UI shows "saved on device" (never "saved").
- Reconnect → queue drains as ONE batched POST per class-day (not per student), every mark lands exactly once.
- Reload the app while offline → the shell loads from the service-worker cache (no white screen).
- Failed read of existing attendance → register is BLOCKED with an error, NOT shown empty-editable.
- Two devices mark the same class-day → converge to one deterministic row (last-write-wins by clamped markedAt).

## Edge Cases
- markedAt more than 2h ahead of server time → clamped to server now, logged.
- Stale replay (older markedAt than the stored row) → skipped by `updated_at <= EXCLUDED` guard, queue still dequeues.
- Unsynced local mark vs a background server refetch on class/date change → the unsynced mark wins (no clobber).
- Teacher with exactly 4 marking days = pass; exactly 3 = fail (threshold boundary).
- Holidays / non-school days excluded from the matrix denominator.
- Service-worker update: a new deploy must refresh the client, not strand it on a cached old shell.

## Critical Paths
- **Offline → reconnect → exactly-once** (E2E): mark offline, kill network, reload, reconnect, assert every mark persisted once. This is the plan's core promise.
- **Read-failure regression** (vitest): `pgGetAttendanceByClassDate` must THROW on DB error, not return `[]` — the register must never show empty-editable for a recorded day.
