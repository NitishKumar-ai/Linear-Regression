## Problem Statement

Temporal is the dominant durable-execution engine for complex workflows, but it is
generic. It has no concept of a plan→execute→review loop, tiered LLM routing (cheap
model for triage, strong model for execution), an agent memory bus, or evaluator-optimizer
patterns. Developers building 24/7 AI agents on Temporal or Celery must re-implement
these AI-specific primitives from scratch every time.

**The gap:** There is no open-source, AI-native orchestration framework purpose-built
for the patterns Anthropic, OpenAI, and Google describe as standard agent architecture
— yet every serious AI agent builder needs them.

## Demand Evidence

- No paying customers yet (pre-product)
- Signal: Temporal reached $5B valuation, $300M Series D (Feb 2026) driven by AI-agent
  demand — the market is clearly here
- Signal: HRD research (done by founder) maps a complete architecture from durable
  execution → LLM routing → memory bus → sandbox isolation → observability
- Gap confirmed: No open-source library exists that packages all five layers as a
  single coherent AI-native framework
- **Missing:** Zero conversations with a specific developer who would use this today;
  this is the next required action before writing code

## Status Quo

Developers building production AI agents today:
1. Bolt LangGraph on top of Redis/Celery for workflow state
2. Self-implement tiered routing (cheap model → strong model) from scratch
3. Use Langfuse or roll their own tracing
4. Pay E2B or Modal separately for sandboxed code execution
5. Implement the evaluator-optimizer loop themselves in every project

There is no integrated layer — developers assemble 5–8 separate services and write glue
code that is thrown away and rewritten at the next company.

## Target User & Narrowest Wedge

**Target:** A senior developer or founding engineer at a Series A–B company running
AI agents in production. Has already felt the pain of assembling the stack themselves.
Knows what Temporal is. Has Postgres and Redis already. Probably building on Python or
TypeScript.

**Narrowest wedge:** **CommitGuard** — an AI security agent that runs on every git push.
Reviews PRs for secrets, vulnerability patterns, and code smells using the plan→execute→review
3-pass loop. Shipped as a GitHub App backed by the framework.

Why CommitGuard is the wedge:
- Continuous trigger (every commit = automatic use)
- Security has existing budget in every company
- Clear, measurable value: "found a leaked AWS key before it hit main"
- The framework's evaluator-optimizer loop is directly visible in every review cycle
- Runs in Firecracker microVM isolation — showcases the sandbox layer
- If a developer adopts CommitGuard and it works, they will ask "how is it built?"
  — that's the framework reveal

## Constraints

- Solo founder; must be buildable while Class-mode/EduAI continues in parallel
- The framework must be open-source (MIT or Apache 2.0) to drive community traction
- CommitGuard MVP must run before any external marketing — dogfood first
- Must run on what developers already have: Postgres + Redis — no new stateful services
  to self-manage. Firecracker/E2B is consumed as an external API (E2B), not self-hosted
- Python-first; TypeScript bindings deferred to after v1 ships
- Per-commit cost cap: CommitGuard must enforce a hard token budget per review
  (default: 50K tokens total, ~$0.03/review at Flash-Lite + Sonnet blended rates)
  to prevent unbounded spend on high-traffic repos

## Approaches Considered

### Approach A: CommitGuard standalone product
- GitHub App only; no framework exposed
- Security tool with AI review under the hood
- Effort: M (~3-4 weeks). Risk: Low.
- Pro: Ships fast, proves demand
- Con: Kills the framework vision; becomes "just a code review bot"

### Approach B: Open-source framework + CommitGuard as hero demo (CHOSEN)
- Build the AI-native orchestration framework (base Agent contract,
  plan→execute→review, tiered routing, Redis memory bus) as an open-source library
- CommitGuard is the reference implementation — shows what you build with it
- Managed cloud service monetizes after GitHub stars + community traction
- Effort: L (~2-3 months). Risk: Medium.
- Pro: Framework compounds; community = inbound for managed service
- Con: Slower to revenue; OSS maintenance is real work solo

### Approach C: Managed Agent Cloud (full HRD)
- Full hosted service: customers define agent config, you run it 24/7
- CommitGuard first, then Research/ML/Marketing agents
- Effort: XL (~3-6 months). Risk: High.
- Pro: Full vision, fundable
- Con: Pre-revenue 24/7 managed infra is high operational burn for a solo founder

## Recommended Approach

**Approach B: Open-source framework + CommitGuard as hero demo**

**Framework architecture (open-source):**
- Python package: `agent-mesh` (or similar) — install via pip
- Core: `BaseAgent` class implementing plan→execute→review durable steps via DBOS
- Tiered LLM router: `LLMRouter` — cheap model (Gemini Flash-Lite) for plan/triage,
  strong model (Sonnet/Gemini Pro) for execute, configurable escalation thresholds
- Memory bus: `AgentBus` backed by Redis Streams with consumer groups
- Observability: OpenLLMetry spans routed to Langfuse by default
- Sandbox: Firecracker/E2B integration via `SandboxedAgent` subclass
- Agent contract: identical to HRD spec (plan/execute/review/read_context/write_event/emit_trace)

**CommitGuard (hero demo, ships first):**
- GitHub App installed on a repo
- On PR open/push: CommitGuard fetches diff, runs plan→execute→review
  - plan: LLM decomposes diff into reviewable segments (Flash-Lite)
  - execute: per-segment secret scan + vuln analysis in Firecracker microVM
  - review: evaluator LLM aggregates findings, rates severity (Sonnet)
- Posts review as a PR comment with severity score
- Self-hosted (user runs their own) — managed version coming later

**Go-to-market sequence:**
1. Build framework (private, docs-first design)
2. Build CommitGuard on top of framework (dogfood on own repos)
3. Ship CommitGuard open-source with framework README
4. Watch GitHub stars; identify companies using it
5. Offer managed CommitGuard + managed framework hosting to early adopters

## Open Questions

- What do we call this? "Agent Mesh" reads like an internal codename; the product
  needs a name that a developer Googles when they're frustrated with Temporal
- Will DBOS (the library) be a hard dependency or optional? It's currently MIT and
  runs in-process — but it's a real dependency with its own maintenance surface.
  Alternative: implement the durable steps interface ourselves and plug DBOS in as
  the default backend, allowing Temporal as a swap-in for teams that already have it.
- CommitGuard as GitHub App requires each self-hosted user to register their own
  GitHub App ID + private key and expose a public webhook URL. This is non-trivial
  setup; v0 should validate with a personal access token + polling before building
  the App registration flow.
- Who are the first 3 developers we want to run CommitGuard before making it public?
  This list should exist before writing the first line of code.
- The plan→execute→review loop needs a precise interface spec before any code:
  what each step receives (Plan, Result types), what triggers retry vs. escalation,
  and how the evaluator's verdict is structured. This belongs in a separate technical
  spec written after demand is validated.

## Success Criteria

**Week 4:** CommitGuard runs on own repos, catches at least one real issue on a real PR
**Week 8:** OSS soft launch — GitHub repo goes public (visible, not promoted); this is
  the soft launch, not "external marketing." Active HN / Twitter promotion comes Month 3.
**Month 3:** 100 GitHub stars + 5 developers running CommitGuard on their own repos
**Month 6:** First company asks for managed version

**Timeline risk buffer:** If DBOS introduces a blocking schema conflict or breaking
change before v1 ships, fallback is implementing the durable steps interface directly
with SQLAlchemy + a simple jobs table (adds ~2 weeks, no new dependencies).

**Pricing hypothesis (managed service, post-OSS traction):**
- CommitGuard managed: $29/month per repo (≤500 PRs/month), $99/month unlimited
- Framework hosting (managed agent runtime): ~$99/month per 1 running agent;
  custom pricing for high-volume customers. Validate with first 3 design partners.

## Dependencies

- DBOS (in-process durable execution library, MIT)
- Redis (developer already has it) + Postgres (developer already has it)
- E2B or self-hosted Firecracker for sandbox
- Langfuse (open-source observability)
- GitHub API for CommitGuard PR integration
- Class-mode/EduAI continues in parallel — this is a new project, not a distraction

## The Assignment

Before writing a single line of code: **find 3 specific developers** — names, GitHub
handles, companies — who are currently building production AI agents and are frustrated
with their orchestration stack. DM them on Twitter/X or email. Ask: "How are you
handling retries and crash recovery for your agents? What breaks most often?" Listen.
If 2 of the 3 say "it's a nightmare, we hacked something together," you have demand
evidence. If they say "we use Temporal and it's fine," you need to rethink the wedge.
