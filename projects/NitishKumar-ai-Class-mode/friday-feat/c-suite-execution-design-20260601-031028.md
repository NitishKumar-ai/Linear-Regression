## Problem Statement

EduAI's current onboarding is a 4-page form flow: school setup → invite teachers → teacher class setup → invite students. It's functional but impersonal — the user fills fields into a form and gets dumped into a dashboard. There's no moment of delight, no personalization signal, and no business intelligence collection.

The founder wants a **conversational onboarding experience** — animated step cards that feel like a modern, premium interaction rather than a government form. Each screen shows one question with micro-animations, collects data that personalizes the product AND feeds business analytics, and ends with a celebration screen showing what was set up.

## Demand Evidence

- No paying users yet (pre-product stage, unchanged from last session)
- Founder has done "something else" to validate but did not elaborate on specifics
- The existing onboarding code suggests the founder has tested the flow internally — the code handles school setup, teacher invites, student invites, and class creation
- New billing infrastructure (Stripe, 4 tiers) suggests the founder is preparing for a paid launch

## Status Quo

Current onboarding flow (4 pages, form-based):
1. `/onboarding/school` — school name, city, board, grades (form fields)
2. `/onboarding/invite-teachers` — email + name + grades per teacher
3. `/onboarding/teacher` — teacher creates classes
4. `/onboarding/invite-students` — student name + parent email + grade + class

Problems with current flow:
- Feels like filling out a government registration form
- No animation, no delight, no personality
- Doesn't collect business intelligence (how did you find us, what tools do you use now)
- No personalization signal — the AI test generator can't pre-configure itself without board/subject data
- No celebration moment — after 4 screens of data entry, you just... land on the dashboard

## Target User & Narrowest Wedge

**Target:** Same as prior design — coaching center owner/teacher in India, or school admin/principal.

**Wedge:** Replace the 4-page form with a 7-screen animated step card flow. Each card slides in with micro-animations. One question per screen. Quick-reply chips for common answers. Celebration screen at the end with personalized summary.

## Constraints

- Must work on mobile (teachers use phones, not desktops)
- Must feed existing PostgreSQL schema — schools table, users table, memberships
- Must integrate with existing auth flow (user is already logged in when onboarding starts)
- Animations must be CSS-only or lightweight JS — no heavy animation libraries
- Must complete in under 2 minutes (7 screens × ~15 seconds each)
- Business intel questions (screens 5-6) must be skippable — only personalization screens (1-4) are required

## Premises

1. The primary user doing onboarding is a school admin, principal, or coaching center owner — not a student. Students get invited later. — AGREED
2. The chat-style experience replaces the current 4-page form flow, not just sits alongside it. — AGREED
3. The business intelligence questions ("how did you find us", "what tools do you use") are secondary to personalization — the user should feel like the questions serve THEM, not you. — AGREED
4. "Animations" means card transitions, chip reveals, progress bar fills — lightweight, fast, mobile-friendly. — AGREED
5. The onboarding data feeds the existing PostgreSQL schema — no new database tables needed for the core personalization flow (screens 1-4). Business intel screens (5-6) use a new lightweight `onboarding_responses` table. — AGREED

## Approaches Considered

### Approach A: WhatsApp-Style Chat Bot
Full chat interface — green bubbles, typing indicator dots, smooth scroll. Scripted conversation tree walks the user through 8-10 questions. Each answer animates as a user bubble.
- Effort: S (1 weekend / CC: ~2 hours)
- Risk: Low
- Pros: Familiar to WhatsApp-heavy Indian educators, ships fast
- Cons: Limited branching, no real AI intelligence, "chat costume on a form"

### Approach B: Animated Step Cards (CHOSEN)
Full-screen animated cards, one question per screen. Cards slide up from bottom with micro-animations. Chips animate in staggered. Progress bar at top. Celebration screen at end with confetti and personalized summary.
- Effort: M (1 week / CC: ~4 hours)
- Risk: Low
- Pros: Visually stunning, cleaner UX for complex inputs (multi-select, file upload), each card can be art-directed independently
- Cons: More design work per card, heavier than a simple chat

### Approach C: AI Concierge
Actual AI-powered chat using Gemini. Adapts questions based on answers.
- Effort: L (2 weeks / CC: ~6 hours)
- Risk: Medium
- Pros: Genuinely adaptive, AI-generated personalized summary
- Cons: AI latency, token cost per session, edge cases

## Recommended Approach

**Approach B: Animated Step Cards** — chosen by the founder.

The step card approach gives the "premium feel" of a modern product while keeping implementation predictable. Each card is a self-contained React component with its own animation. The flow is linear (no branching), which makes it fast to build and test.

## The 7-Screen Flow

### Screen 1: Role Selection
- **Question:** "What best describes you?"
- **Input:** 4 chips — School Owner/Principal, Teacher, Coaching Center Owner, Tutor
- **Animation:** Card slides up from bottom (300ms ease-out), chips stagger in (50ms delay each)
- **Data feeds:** `users.role` + `users.user_type` (see Role Mapping below)

**Role Mapping (chip label → DB values):**

| Chip Label | `users.role` | `users.user_type` (new, for BI) |
|---|---|---|
| School Owner / Principal | `principal` | `school_owner` |
| Teacher | `teacher` | `teacher` |
| Coaching Center Owner | `school_admin` | `coaching_center_owner` |
| Tutor | `teacher` | `independent_tutor` |

`users.role` stays within the existing CHECK constraint (`student`, `teacher`, `parent`, `principal`, `school_admin`, `admin`). `users.user_type` is a new TEXT column for business intelligence — no constraint, free-form.

### Screen 2: Institution Info
- **Question:** "What's your institution called?"
- **Input:** Text field for name, text field for city
- **Animation:** Card slides up, text fields fade in
- **Data feeds:** `schools.name` (SQL: `name`), `schools.city` (SQL: `city`)

### Screen 3: Board & Subjects
- **Question:** "Board & subjects"
- **Subtitle:** "We'll personalize your AI tools based on this."
- **Input:** Board chips (CBSE/ICSE/State/IB/Other), Subject multi-select chips
- **Animation:** Board chips animate first, then subject chips after board is selected
- **Data feeds:** `schools.board` (SQL: `board`), `users.subjects` (SQL: `subjects text[]` — already exists, write as string array)

### Screen 4: Size & Grades
- **Question:** "How big is your institution?"
- **Subtitle:** "This helps us recommend the right plan for you."
- **Input:** Grade multi-select chips, student count range chips (1-50, 50-200, 200-500, 500+)
- **Animation:** Grade chips stagger in, student count chips appear after at least one grade selected
- **Data feeds:** `schools.grades_offered` (SQL: `grades_offered text[]`), new `schools.approximate_students` column (SQL: `approximate_students TEXT`)

### Screen 5: Current Tools (Business Intel — Skippable)
- **Question:** "What do you use today?"
- **Subtitle:** "So we can show you what EduAI replaces."
- **Input:** Multi-select chips — WhatsApp groups, Google Classroom, Paper registers, Excel/Sheets, Another app, Nothing
- **Skip button:** Yes (bottom of card, small text)
- **Animation:** Cards slide up, chips stagger
- **Data feeds:** `onboarding_responses` table (new — lightweight JSON store for business intel)

### Screen 6: Discovery Source (Business Intel — Skippable)
- **Question:** "How did you find us?"
- **Subtitle:** "Helps us reach more educators like you."
- **Input:** Single-select chips — Google search, Friend/colleague, Social media, YouTube, WhatsApp forward, Other
- **Skip button:** Yes
- **Data feeds:** `onboarding_responses` table

### Screen 7: Celebration
- **No question** — pure celebration
- **Confetti animation** burst on mount
- **Personalized summary box:** Shows institution name, city, board, subjects, grades, student count — all from screens 1-4
- **CTA box:** "Your first AI-generated test is free — upload any chapter PDF and get 20 MCQs in 30 seconds"
- **Button:** "Enter your workspace →"
- **Data action:** Sets `users.onboardingComplete = true`, creates workspace if not exists

## Animation Spec

| Element | Animation | Duration | Easing |
|---------|-----------|----------|--------|
| Card entrance | translateY(100%) → translateY(0) | 300ms | ease-out |
| Card exit (back) | translateY(0) → translateY(100%) | 200ms | ease-in |
| Chip stagger | opacity 0→1, scale(0.95)→scale(1) | 200ms per chip | ease-out, 50ms stagger |
| Progress bar fill | width transition | 400ms | spring (CSS: cubic-bezier(0.34, 1.56, 0.64, 1)) |
| Text input focus | border-color transition | 200ms | ease |
| Celebration confetti | canvas-confetti library (3KB) | 2000ms | — |
| Summary box | opacity 0→1, translateY(20px)→0 | 400ms | ease-out, 200ms delay after confetti |

## Data Model Changes

### New: `onboarding_responses` table (business intel only — screens 5-6)
```sql
CREATE TABLE IF NOT EXISTS onboarding_responses (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  question_key TEXT NOT NULL,           -- e.g. 'current_tools', 'discovery_source'
  response JSONB NOT NULL,              -- flexible: ["WhatsApp groups", "Paper registers"]
  created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_onboarding_responses_user ON onboarding_responses(user_id);
```

### Modified: `schools` table
```sql
ALTER TABLE schools ADD COLUMN IF NOT EXISTS approximate_students TEXT;
-- Values: '1-50', '50-200', '200-500', '500+'
```

### Modified: `users` table
```sql
-- user_type is new — free-form BI field for the onboarding role chip
ALTER TABLE users ADD COLUMN IF NOT EXISTS user_type TEXT;
-- subjects already exists as text[] — no migration needed
-- Just write to it: UPDATE users SET subjects = '{"Physics","Chemistry"}' WHERE id = $1
```

**Note:** `users.subjects` already exists as `text[] DEFAULT '{}'::text[]'` (not JSONB). The onboarding flow writes to it as a string array. No schema change needed for subjects.

## Migration Strategy

- Users with `onboarding_complete = true` → skip entirely, never shown the new flow
- Users with `onboarding_complete = false` (or NULL) → redirected to the new `/onboarding` flow
- Old routes (`/onboarding/school`, `/onboarding/invite-teachers`, etc.) → redirect to `/onboarding` (new)
- Old backend endpoints (`POST /api/school/setup`, etc.) → kept as-is, not removed (other code may depend on them)
- The new flow writes to the same tables as the old flow — no data migration needed

## Error Handling & Resume

- Progress is persisted after each step server-side (each `POST /api/onboarding/step` writes immediately)
- On page load, query `GET /api/onboarding/progress` which returns the last completed step number
- If the user closes the browser mid-flow, they resume from the last completed step on next login
- If a step API call fails, show an inline error toast and let the user retry — do NOT restart from screen 1
- If the server is unreachable, buffer the response client-side and retry on reconnect (simple retry, not offline-first)

## Auth Middleware

The new `POST /api/onboarding/step` endpoint uses `authenticateToken` middleware from `server/middleware.ts`. This already supports both auth paths (JWT verify → session lookup fallback), so it works for both Firebase legacy users and self-hosted PostgreSQL auth users. The user ID is extracted via `req.session.userId` (self-hosted) or `(req as any).user.id` (JWT), consistent with existing route patterns.

## Endpoint Schema

The `POST /api/onboarding/step` endpoint accepts a discriminated union:

```typescript
type OnboardingStepPayload =
  | { step: 'role'; data: { role: 'principal' | 'teacher' | 'school_admin'; userType: string } }
  | { step: 'institution'; data: { name: string; city: string } }
  | { step: 'board_subjects'; data: { board: 'CBSE' | 'ICSE' | 'State' | 'IB' | 'Other'; subjects: string[] } }
  | { step: 'size_grades'; data: { grades: string[]; approximateStudents: '1-50' | '50-200' | '200-500' | '500+' } }
  | { step: 'current_tools'; data: { tools: string[] } }        // skippable
  | { step: 'discovery'; data: { source: string } }             // skippable
  | { step: 'complete'; data: {} }                               // triggers workspace creation + onboardingComplete
```

Validation uses Zod discriminated union on `step` field. Each step writes to the appropriate table:
- `role` → `users.role` + `users.user_type`
- `institution` → `schools.name` + `schools.city` (upsert via `pgUpsertSchool`)
- `board_subjects` → `schools.board` + `users.subjects`
- `size_grades` → `schools.grades_offered` + `schools.approximate_students`
- `current_tools` → `onboarding_responses` (question_key: 'current_tools')
- `discovery` → `onboarding_responses` (question_key: 'discovery_source')
- `complete` → creates workspace (type: 'school', name: school name, owner: current user), sets `users.onboarding_complete = true`

## Workspace Creation on Complete

When step `complete` fires:
1. Check if user already has a workspace → if yes, skip creation
2. Create workspace: `type = 'school'`, `name = school.name` (from screen 2), `ownerId = currentUser.id`
3. Add the user as workspace owner via `pgUpsertMembership`
4. Set `users.onboarding_complete = true`
5. Return `{ workspaceId, redirectUrl: '/dashboard' }`

## Onboarding Guard Logic

The updated `use-onboarding-guard.ts` hook:
```typescript
// Redirect logic:
// - If user.onboardingComplete === true → no redirect (let them through)
// - If user.onboardingComplete === false AND current path is NOT /onboarding → redirect to /onboarding
// - If user.role === 'student' → skip onboarding entirely (students are invited, not onboarded)
```

Roles that see onboarding: `teacher`, `principal`, `school_admin`. Roles that skip: `student`, `parent`, `admin`.
