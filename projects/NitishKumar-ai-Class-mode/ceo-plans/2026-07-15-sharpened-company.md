## Vision

### 10x Check
The 10x version of this 90-day plan is not more product — it is "one paying school **plus a repeatable path to school #2**." One paying school proves a customer exists; a second principal conversation run from a written playbook proves a company exists. Everything accepted below serves one of those two proofs.

### Platform Potential
The per-workflow usage-logging task (design doc objective 3) is the seed of the learning-record layer: same event stream, different aggregation. Build the logging schema knowing it will one day feed per-student records — but do not build the records until the graduation trigger fires (money received or signed written commitment).

## Accepted Scope (added to this plan)
- School #2 playbook (one page: pitch, objections heard, onboarding steps) written within a week after the WTP conversation, whatever its outcome; one second-principal conversation **held** (not merely booked) before day 90.
- Term report: one-page principal-facing artifact from real school data (attendance summary, fee position, class trends). Honest numbers only; thin data renders as visibly thin, never padded. Built before the WTP conversation and physically handed over during it, alongside the paid-pilot offer. **Build constraints (binding, from review findings — each is a documented past incident in this repo):** (1) tenant gate checks role first and 403s on null schoolCode, fail closed, with a hostile cross-school regression test; (2) no reuse of any analytics path that ever fabricated values; (3) thin data renders honestly thin; (4) query failure shows a visible error, never a blank-but-plausible report; (5) rendered from code — nothing read from disk at runtime (Dockerfile COPY trap).
- Offline-first attendance capture (conditional on wedge selection), scoped to the **web app/PWA** — not classmode-mobile, whose phases stay demand-gated. **v1 narrowed per outside-voice review:** durable local queue persisting across page reload and app restart; idempotent sync on next app-foreground (no wall-clock sync guarantee — a PWA cannot promise one while Android may suspend it); sync failures surface visibly to the teacher, never dropped silently; single-device-per-teacher assumption documented. **Conflict rule: the server rejects stale writes via a version check and surfaces conflicts for teacher review — last-write-wins is disallowed** (it can silently replace a corrected statutory-adjacent record with stale offline data). Auth-expiry handling, multi-device, and shared-device privacy hardening go to TODOS.md. Effort relabeled **L** if scope grows past this.
- Vernacular teacher UI for the selected wedge workflow, native-speaker checked. **Dictionary-first edits plus a test** asserting the wedge-screen keys resolve to the new vernacular strings — `t(key, fallback)` returns the dictionary value whenever the key exists, so fallback-only edits silently no-op (this bit prod once already).
- **Custodial baseline** (added from outside-voice review — the boring work that makes a system of record credible, and exportability is the direct answer to "dependence = lock-in"): one tested backup restore, one-click data export (CSV/PDF) for the school's own records, an audit trail on record corrections, and a one-page data policy for minors' data (consent, retention, deletion, breach contact). Remaining custody items to TODOS.md.
- **Weekly metrics script** (`npm run metrics:weekly`): founder-facing printout of the probe metrics with definitions, baseline week, and decision thresholds fixed before collection starts. Metrics derived from existing domain tables first; minimal `usage_events` insert only for read/view actions. Dashboard deferred to TODOS.md.
- TODOS.md revived: carries provider-swap canary (post-graduation-trigger), learning-record schema (post-trigger), plus all future deferrals.
- Manual daily absence summary to the pilot principal, from real data, labeled as a manual preview. **"WTP week" defined:** summaries start 3 school days before the scheduled WTP conversation (or as many as scheduling allows) and continue through any within-week reschedule until the conversation happens. **Hard stop:** the manual summary ends no later than the day the "unprompted" cutoff date is declared for the wedge streak — it never runs concurrently with streak measurement, so it can never taint or reset the 30-school-day clock.

## Sequencing Guards (binding)
1. **The WTP close attempt ships first, in audit-then-ask order.** The school visit opens with the one-hour workflow audit, then the conversation with the paid-pilot offer — both inside week 1. No accepted expansion may delay it. The term report (2.2) is scoped to what can be built before that conversation; if it is not ready, the conversation happens anyway.
2. The design doc's day-30 fail line applies to ALL accepted expansions, with the **escalation consequence** (not a freeze): no written WTP answer by day 30 means 2.1–2.4 build work pauses and the only permitted work is escalation — the mapped real buyer, then a second school.
3. Objective ordering within the 90 days: WTP question → wedge audit → wedge-serving work (2.3, 2.4) → streak measurement. Expansions never run ahead of the audit that justifies them.
4. **No accepted expansion may delay the day-14 probe preconditions** (Gemini billing linked, usage logging shipped — design doc objective 3). If week-1 time collides between the term report and usage logging, usage logging wins; the term report degrades to whatever is ready by conversation day, per guard 1.
5. Guard 2's day-30 pause covers 2.1–2.4 explicitly; 2.5 completes in week 1 and 2.6 self-terminates at the WTP conversation, so neither survives to day 30 in any scenario.

## Design Specifications (added by /autoplan design phase — binding for implementation)

### Term report (2.2) — visual spec
- **Hierarchy, top to bottom:** (1) school name + term dates + "prepared from your school's own records"; (2) the single strongest true number as the headline (e.g., "1,240 attendance entries recorded by your teachers this term"); (3) per-workflow sections in descending data-strength order — weakest last, never hidden; (4) footer: data window, generation date, "no estimated or filled-in values appear on this page."
- **Thin-data rules:** every audited workflow appears; unused ones render an explicit named empty state ("Marks: not yet in use at your school"), never omitted. Each section carries its denominator ("attendance recorded on 34 of 41 school days"). Trends suppress below a minimum denominator instead of extrapolating. Query failure prints "could not be generated" — a report with an error block is regenerated, never handed over.
- **Minimum viable report (guard-4 degradation floor):** header + strongest number + coverage footer. Below that, no report is handed over.
- **Print constraints:** A4 portrait, grayscale-safe, survives a cheap inkjet and a photocopy, school-letterhead register aesthetic, tabular, no clipped tables. Not a dashboard screenshot.
- **Language:** bilingual — vernacular headings, Latin digits (Indian schools mix scripts freely; labels vernacular, numerals Latin). Same native-speaker check as 2.4.
- **Privacy:** aggregates and class-level trends only; no individual student names on v1 (a paper artifact has no access control).
- **Separation:** the report and the paid-pilot offer stay separate pages; a report with a price on it is a flyer.

### Attendance screen + offline states (2.3) — interaction spec
- **Mobile-first order (360px portrait):** today's date + remembered per-teacher class at top (no daily re-selection); "All present — mark exceptions" as primary action; sticky Save with inline sync status; roster below. No horizontal scrolling.
- **Persistent day-status line** (not toasts): "Today: saved ✓ / saved on this phone, waiting to send (3) / synced at 10:42 / problem — tap". The teacher can always answer "is today's attendance safely recorded?" from one glance. Toasts demoted to supplements.
- **State matrix (each with one sentence of vernacular copy):** offline-detected; queued-locally (count); syncing; synced-confirmed; sync-failed-retryable; sync-rejected-stale (conflict); storage failure; auth-expired-with-queued-data (fix deferred, but the state must show "sign in again — your marks are safe on this phone", never silent loss).
- **Conflict review flow:** only students whose status differs; both values in plain words ("Your phone says Absent · School record says Present"); two large vernacular buttons per row + "keep all school records" bulk action; cannot be dismissed without choosing; navigating away preserves unresolved conflicts; every resolution lands in the corrections audit trail (custodial baseline).
- **Touch and access floors:** 44px minimum targets (current status buttons are h-8/32px — below floor), WCAG AA contrast, visible focus, status never conveyed by color alone.
- **Status taxonomy:** mirror the school's paper register marks (captured in the workflow audit) — do not default to Present/Absent/Late/Excused if the register uses P/A.

### Vernacular pass (2.4) — restated scope (code-verified)
The wedge screen (`client/src/pages/attendance.tsx`) does not call `t()` at all and `client/src/lib/i18n.tsx` has no non-English locale — the "dictionary-first" instruction alone no-ops. Actual scope: wire `t()` through the wedge screen including all toast/error/confirmation copy (~30 strings), add the pilot school's locale block (language named by founder — open decision), add a visible persisted language switcher (setLocale exists, no UI), handle text expansion, then the key-resolution test. Effort relabeled **M**.

### Honesty copy audit (immediate, pre-WTP)
The attendance page currently promises automated WhatsApp parent notification and toasts "N parent(s) notified" while the pipeline is paused — fabricated feedback to real accounts, on the wedge screen, violating the constitutional invariant. Remove or truthfully reword before the WTP visit. (Spawned as its own fix task.)

## Engineering Specifications (added by /autoplan eng phase — binding for implementation)

**Auto-decided on principle, flagged in the audit trail:**
- **E1 (DRY):** no new `usage_events` table — the existing `feature_usage` table + `pgTrackFeatureUsage` (fire-and-forget, self-logging, indexed) is exactly the specced pipeline. Read events use namespaced feature strings (`attendance_view`, `report_view`). The day-14 task shrinks to wiring view-event calls + writing `scripts/metrics-weekly.ts`.
- **E2 (metrics reproducibility):** event definitions, baseline, and thresholds live in the script; each weekly run appends its output to a persisted snapshot (table or committed JSON) so baselines can't silently shift on retries or redefinitions.
- **E3 (term model, minimal):** term report v1 derives "school days" from days-with-any-attendance plus founder-entered term start/end dates. No holiday-calendar table in v1; the 30-school-day streak counts observed school days.
- **E4 (honest naming):** the fees section renders as "Fee records summary" (pending/paid/waived counts and amounts) — never "fee position"; the schema has no receipts/partials/refunds and the report must not imply it does.
- **E5 (typed report queries):** report query helpers take `schoolCode: string` (non-optional) and throw on error — never return `[]` on failure (the existing `[]`-on-error convention is how honest-thin silently becomes empty). Platform-admin cross-school reporting excluded from v1.
- **E6 (report route security):** normal authenticated route behind `authenticateToken` + `resolveTenantScope`; `Cache-Control: no-store`; no tokenized share links; each generation logged to `audit_events`.
- **E7 (corrections atomicity):** any correction/conflict resolution writes the domain row and the before/after `audit_events` entry in one transaction; the current audit helper's swallow-on-failure path is not acceptable on this route.
- **E8 (custody — records survive deletion):** `attendance` and `fees` FKs move off `ON DELETE CASCADE` (RESTRICT + soft-delete for students) — deleting a student must not erase statutory-adjacent history. Additive `ALTER` fits the idempotent-schema pattern.
- **E9 (offline write-path contract — spec recorded, execution pending the gate decision on 2.3):** integer `version` column on attendance; GET returns versions; POST carries a client batch UUID (side-effect dedupe: no duplicate WhatsApp sends or feature_usage rows on replay) + expected versions; server returns per-row outcomes `{written, conflicts[]}` — partial success, non-conflicting rows commit. A terminal "window-expired" queue state covers the 3-day backfill limit (festival breaks WILL exceed it) with an admin-backfill escalation. True scope of 2.3 including PWA read-path caching and the attendance page state-model rewrite: **L–XL, not M.**

**Known-bug guardrails (spawned as immediate fix tasks):** the fabricated WhatsApp-notified toast on the wedge screen; `user.school_code` → NULL school_code on admin attendance writes (server/routes/attendance.ts:115).

**What already exists (reuse, don't rebuild):** `feature_usage` + writer; `audit_events` table; `(school_code, class_name, date)` and fees indexes; `resolveTenantScope`; the server-authoritative date window (W-6); the idempotent schema migrate; the regression-test-per-incident pattern (8e3d2b8).
