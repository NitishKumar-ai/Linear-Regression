## Problem Statement

Class-mode is a multi-tenant school management SaaS (attendance, fees, WhatsApp
parent alerts, AI tutor) live at classmode.inmodel.in. It is feature-rich but
unfinished in the only way that matters: a real school that signs up through the
front door cannot use the product. The July 2 full-journey QA scored it 48/100
with 3 critical findings, and the only "pilot school" is a seeded simulation
(`server/scripts/seed-pilot.ts`), not a customer. "Finish this project" therefore
means: fix the activation chain, remove the trust-killing fake data, and put one
real school on it with observed usage.

## Demand Evidence

Honest current state: none recorded. No real school uses the product. The pilot
school is simulated. No payment, no usage panic, no pull. This is the largest
open risk and the reason the recommended approach includes onboarding a real
school with observation — the code work below is necessary but not sufficient.
The `feature_usage` table (#270) exists and is the designated instrument for
converting "we think schools want this" into a query.

## Status Quo

For the target school (Indian K-12, the market the WhatsApp-first parent loop and
₹-denominated fees imply): attendance lives in a paper register or an Excel
sheet; parents learn about absences at day's end or never; fee follow-up is a
clerk with a phone making calls. The workaround costs are real but currently
assumed, not verified with a named school — see The Assignment.

## Target User & Narrowest Wedge

- **Target human (to be named — this is the assignment):** a principal or
  school administrator at one specific school who personally answers to parents
  when a child is absent and unaccounted for.
- **Narrowest wedge (already built, currently broken at the front door):**
  teacher marks attendance → absent student's parent gets a WhatsApp within
  minutes → fee reminders ride the same parent-phone rail. One sentence a
  principal understands: "Parents know within 5 minutes when their kid is absent."

## Constraints

- Solo founder + AI tooling; no team.
- Production is live and serves the broken activation chain today; fixes ship
  through the existing GitHub Actions CD on merge to main.
- `feat/redis-event-bus` (v1.8.2.0) merged to main (c86508c) during this
  session; production rollout must be verified so absence alerts are
  crash-durable during the pilot.
- Tenant isolation invariant is non-negotiable: null schoolCode fails closed;
  fixes must provision the tenant key, never weaken the guard.
- Dev environment: `npm run migrate` requires pgvector; dev compose uses
  postgres:16-alpine without it (known operational pitfall).

## Premises

1. "Finished" = one real school actively using attendance/fees weekly on a paid
   or committed-to-pay arrangement — not feature-completeness. (Agreed)
2. The front-door activation chain (signup → school linked → teachers invited →
   class created → attendance marked → parent WhatsApp fires) IS the product;
   Learn Hub, SIS, Study Arena, analytics are supporting cast until it works. (Agreed)
3. No new features until the six activation blockers are fixed and verified by
   re-running the same QA journey. (Agreed)

## Approaches Considered

### Approach A: Activation Sprint (minimal viable)
Ship `feat/redis-event-bus`, then one fix branch for the six blockers
(ISSUE-001/010/008/009/002/006), verified by re-running the QA journey.
Effort S (human ~1 week / CC ~1–2 days). Risk Low. Launchable, but leaves fake
demo data in place and produces zero demand evidence.

### Approach B: Pilot-Proof (chosen)
Everything in A, plus remove or clearly badge every fabricated data surface
(ISSUE-003/011), fix swallowed-error patterns (ISSUE-002 UX, ISSUE-005,
ISSUE-012 copy), then onboard one real school with the founder watching their
first attendance session, instrumented via `feature_usage`.
Effort M (human ~2–3 weeks / CC ~3–4 days of fixes + real-world time). Risk
Medium — the risk is finding the school, not the code.

### Approach C: Attendance-Only Wedge (lateral)
A's fixes plus feature-flag everything except attendance + WhatsApp + fees for
pilot schools. Sharpest sales sentence, fewest broken surfaces exposed; hides
months of Learn Hub work and delays learning whether the wider product matters.

## Recommended Approach

**Approach B — Pilot-Proof.** A gets you launchable but still evidence-free.
B is A plus trust surfaces plus the one thing code cannot produce: a real
teacher observed using it. C remains available as a *sales posture* on top of B
(lead the pitch with the wedge) without flagging features off.

### Workstream 2 — Activation chain fixes (all root-caused in QA report
`nitish-chore-docker-folder-test-outcome-20260703-020936.md`)
1. **ISSUE-001 (Critical):** onboarding must provision `school_code` and a
   membership row, not just `schoolId` (`server/routes/onboarding.ts:194`;
   guard at `server/lib/tenant.ts:52` stays fail-closed). Backfill existing
   broken rows via an idempotent statement appended to `scripts/pg-schema.sql`
   (so AUTO_MIGRATE applies it at boot in every environment): set
   `users.school_code` from the school row referenced by `users.school_id`
   where `school_code IS NULL`, and insert the missing rows into `memberships`
   (`status='active'`, role key taken from `users.role`, `ON CONFLICT DO
   NOTHING` so re-runs are true no-ops). If `membership_roles` wiring is needed
   for permissions, mirror whatever the invite-accept path
   (`pgUpsertMembership`) creates — the backfilled state must be
   indistinguishable from a correctly-onboarded school. Post-deploy
   verification (added to the acceptance artifact): the count of users with
   `school_id` set and `school_code IS NULL` must be 0.
2. **ISSUE-010 (Critical):** `authenticateToken` must include `schoolCode` in
   `req.user` (`server/middleware.ts:50`) — without this, fixing #1 still
   leaves attendance/fees 403 for every role.
3. **ISSUE-008 (Critical):** unify class routes — client calls `/api/classes[/mine]`,
   server mounts them under `/api/onboarding/classes`. Canonical path:
   **`/api/classes`** (classes outlive onboarding; move/remount the handlers
   rather than pointing the client at an onboarding-scoped path). Keep the old
   `/api/onboarding/classes*` mount as an alias for one release so cached SPA
   bundles don't break, then remove it. Make the teacher quest reflect DB truth
   (no success UI on 0 rows). Unblocks invite-students
   (`invite-students.tsx:17`). **Reconciliation note:** in-progress work in the
   working tree currently points the client at `/api/onboarding/classes/mine` —
   the opposite direction; align it with this decision before merging.
4. **ISSUE-009 (High):** add an `/api/*` 404 JSON guard before the SPA
   catch-all so mis-mounted routes can never again masquerade as 200 HTML.
5. **ISSUE-002 (High):** make `npm run migrate` work against dev compose
   (pgvector-enabled image or gated vector DDL), and surface onboarding-complete
   failures to the UI instead of hanging on "Completing setup…".
6. **ISSUE-006 (Low, but chain-blocking):** give `principal` role a working
   invite-teachers path (route guard + sidebar item + non-404 route).

### Workstream 3 — Trust surfaces
7. **ISSUE-003/011:** demo data defaults OFF for non-demo schools; every panel
   respects the toggle (events, notifications, calendar, analytics, student
   streak/XP, teacher benchmark). Mechanism: **`is_demo` boolean on `schools`,
   default false** (the only option grounded in the schema; no demo school-code
   constant exists in the codebase); a self-registered school must never see
   fabricated numbers. Sizing note — this is likely the **largest single item**
   in the fix list, because demo content lives in three distinct mechanisms
   that must each be handled: (a) per-component client state defaulting to
   demo-ON (`principal-dashboard.tsx:46`, `useState(true)`), (b) server-side
   `?demo=true` params (`analytics.ts:405,515`), and (c) hardcoded
   `data || mockData` fallbacks (`performance-chart.tsx:39`,
   `top-students.tsx` `students || mockStudents`) that render fake data
   whenever an API returns nothing regardless of any toggle — those fallbacks
   must be **deleted**, not toggled. Intended behavior: for `is_demo=false`
   schools, the demo toggle is hidden and the server ignores `?demo=true`;
   the toggle exists only for demo schools. Fabricated numbers shown to a real principal are a trust killer in
   a B2B sale to people responsible for children's records.
8. **ISSUE-005/012:** replace friendly-empty-state masking of 403s with the
   honest-error pattern the Student Directory already uses ("Failed to load
   students… Retry"); fix the "check your internet" copy on server failures.
   Also align AI usage metering on **`ai_usage_logs`** (the table that exists
   in `scripts/pg-schema.sql:487`) by fixing the query in
   `server/lib/pg-queries.ts:2102` — kept in this workstream because unmetered
   AI usage is a live cost/abuse exposure the moment a real school is on the
   product, and the fix is a one-line table-name change.
9. **ISSUE-007 (Low, cosmetic):** Recharts width/height console warnings on the
   principal dashboard — fix opportunistically while touching those panels for
   item 7; not a gate.

## Open Questions

- **Q1 (demand):** What evidence exists that a specific school wants this?
  Currently none recorded — resolved only by the pilot.
- **Q3 (named human):** Who is the principal? Name, school, and the consequence
  they personally face when attendance/fees go untracked.
- **Pricing shape:** `server/routes/billing.ts` is Stripe per-user tiers, but the
  buyer is a school and the market is India (Stripe availability + UPI norms);
  school-level pricing (likely Razorpay or manual invoicing for pilot #1) is
  unresolved. For the pilot, a signed commitment or manual invoice beats
  building billing.
- **ISSUE-004 (Messages WebSocket dead) and ISSUE-013 (subject mislabeling):**
  fix during pilot only if the school touches those surfaces; not activation-chain
  blockers.

## Success Criteria

1. QA journey re-run: 0 critical, 0 high findings on the activation chain;
   health score ≥ 85/100.
2. A brand-new self-registered school can, unaided: link tenant, invite a
   teacher, create a class, enroll students, mark attendance, and trigger a real
   parent WhatsApp — verified end-to-end in production.
3. One real school: ≥1 teacher marks attendance on 3 consecutive school days
   (via `feature_usage`), ≥1 absence alert delivered to a real parent.
4. A payment or written commitment to pay from that school.
5. Founder has one written observation note containing at least one surprise.

- Gemini/AI keys healthy in production if the school touches Learn Hub
  (boot health check exists; ISSUE-012 copy fix reduces blast radius).
- Access to one real school — the founder's job, no code dependency.
