## Problem Statement

After completing the 7-step signup wizard (school name, board, subjects, grades), users land on the dashboard with no guidance on what to actually *do*. The signup flow collects setup info — it doesn't teach the product. There is no empty-state guidance, no feature tour, no nudge toward the first meaningful action.

The goal: a gamified quest system that teaches the three core activation events, starting with checklist mechanics (v0) and upgrading to XP/levels (v1).

## What Makes This Cool

Users don't read docs. They click around and either "get it" or leave. A quest panel solves this by giving them a concrete list of things to try — with visual reward when they do it. The "whoa" moment is: a teacher fills in their first test (title, subject, class, question types), hits submit, and immediately sees their quest check off with confetti. In one action they've understood what this app is for. Same payoff when they set up their first class and invite their first student.

## Constraints

- Three quest targets: generate a test (`POST /api/tests`), create a class (`POST /api/classes`), invite a student (`POST /api/invite/student`)
- All three quests are scoped to the `teacher` role only — `school_admin`, `student`, `parent`, `principal` roles see no panel
- v0: localStorage state (no backend changes)
- v1: Postgres — add `quest_progress JSONB` to users table + `PATCH /api/auth/me/quests`
- Detection via TanStack Query mutation `onSuccess` callbacks (already used throughout the app)
- Show panel only for the first 7 days from `firstSeenAt` OR until all quests are done, whichever comes first. Measured from the first authenticated page view by a teacher (effectively: the first time any `Layout`-wrapped page loads) — not from signup date.
- Dismiss behavior: X button hides the panel body but the floating button remains visible (with progress count) until all quests are done or the 7-day window closes. Pressing the floating button after dismissal re-opens the panel.
- Mobile-responsive (teachers use phones)
- Accessibility: `QuestButton` has `aria-label="Open quest checklist"`; `QuestPanel` has `role="complementary" aria-label="Quest checklist"` (not `role="dialog"` — `aria-modal` would require a focus trap which is overkill here; `complementary` is correct for a sidebar-style panel); Escape key closes the panel (sets `panelDismissed: true`); panel body uses `overflow-y-auto max-h-[80vh]` to handle small screens with soft keyboards open
- z-index: `QuestButton` at `z-[70]` (above sidebar's `z-[60]`); `QuestPanel` at `z-[72]`. Note: `test-page.tsx` has a bottom-right FAB at `z-[70]` — verify no visual overlap on that page; teachers can view test pages. If overlap occurs, bump to `z-[75]`/`z-[77]`.

## Premises

1. Users arrive at the dashboard post-signup with no guidance — the signup flow is a form, not a tutorial.
2. The three actions (generate a test, create a class, invite a student) are the right activation events — doing all three means the user "gets" the product.
3. Quest/XP language will appeal to the target audience (phone-native teachers familiar with Duolingo-style apps).
4. Quest state needs to persist across devices (Postgres for v1, acceptable to start localStorage for v0).
5. The quest panel is a layer on top of the existing dashboard, not a replacement for any route.

## Approaches Considered

### Approach A: Setup Checklist (Minimal)
Collapsible panel, 3 checkboxes, deep-link buttons, confetti on completion. localStorage only.
- Effort: S (1-2 days / CC: ~1 hour)
- Risk: Low
- Pros: Ships fast, zero backend changes, proven pattern
- Cons: Not genuinely gamified — it's a checklist. No XP to learn from.

### Approach B: Quest Panel with XP + Level-Up
Floating button, slide-in panel, XP rewards, level-up animations. State in Postgres.
- Effort: M (3-4 days / CC: ~3 hours)
- Risk: Medium — API detection coupling is the tricky part
- Pros: Teaches full gamification mechanics. Real "whoa" UX.
- Cons: Requires backend DB migration + new endpoint.

### Approach B+A (CHOSEN): Panel v0, XP v1
Build the panel and visual mechanics in v0 (localStorage). Wire XP/levels as a second pass once the structure works.
- Effort: v0: S (1-2 days / CC: ~1 hour). v1: +M (2-3 days / CC: ~2 hours)
- Risk: Low for v0, Medium for v1

interface QuestProgress {

**Detection (v0 — client-side mutation hooks):**

Hook into TanStack Query `useMutation` `onSuccess` callbacks in the relevant pages:

| Quest | File | Mutation |
|---|---|---|
| `quest:create-test` | `client/src/components/test/test-details-form.tsx:89` | `createTestMutation` — `POST /api/tests` |
| `quest:create-class` | `client/src/pages/onboarding/teacher-class-setup.tsx:22` | `createMutation` — `POST /api/classes` |
| `quest:invite-student` | `client/src/pages/onboarding/invite-students.tsx:28` | `sendMutation` — `POST /api/invite/student` |

In each mutation's `onSuccess`, call `markQuestComplete` with the correct quest ID:
- `test-details-form.tsx createTestMutation.onSuccess` → `markQuestComplete("quest:create-test")` — fires on both "Continue to Questions" and "Save Draft" button paths (both call the same mutation). Both count as completing the quest. **Implementation note:** call `markQuestComplete` as the first line of `onSuccess`, before `setLocation(...)`. The existing redirect to `` `/tests/${test.id}/questions` `` points to a route that does not exist in `App.tsx` (pre-existing bug) — `markQuestComplete` must fire before any redirect to avoid losing the call.
- `teacher-class-setup.tsx createMutation.onSuccess` → `markQuestComplete("quest:create-class")` — precondition: teacher must have `schoolId` set; if the `POST /api/classes` returns a 400 ("Not linked to a school"), `onSuccess` never fires and the quest stays incomplete. Teachers invited directly (without school setup) may hit this — acceptable for v0; v1 can add a guard.
- `invite-students.tsx sendMutation.onSuccess` → `markQuestComplete("quest:invite-student")` — the invite page requires a class to exist (class selector populated from `/api/classes/mine`; Send Invite button disabled without a classId). Do NOT add a `completedIds`-based guard in `QuestItem` — existing teachers with classes wouldn't have quest:create-class in localStorage, and would be incorrectly blocked. The invite page's own disabled-button state is the right UX gate.

**`markQuestComplete` — exact implementation contract:**
```typescript
// use-quest-progress.ts (exported plain function, NOT a hook)
export function markQuestComplete(questId: string): void {
  const raw = localStorage.getItem(QUEST_STORAGE_KEY);
  const progress: QuestProgress = raw ? JSON.parse(raw) : defaultProgress();
  if (progress.completedIds.includes(questId)) return; // idempotent
  progress.completedIds = [...progress.completedIds, questId];
  localStorage.setItem(QUEST_STORAGE_KEY, JSON.stringify(progress));
  window.dispatchEvent(new Event("quest-updated"));
}

// useQuestProgress hook — reads state + subscribes to updates
export function useQuestProgress() {
  const [tick, setTick] = useState(0);
  useEffect(() => {
    const handler = () => setTick(t => t + 1); // forces re-render
    window.addEventListener("quest-updated", handler);
    return () => window.removeEventListener("quest-updated", handler);
  }, []);
  const progress = readProgressFromStorage(); // reads localStorage on every render
  return { progress, markQuestComplete };
}
```

**localStorage key:** `const QUEST_STORAGE_KEY = "classmode:quest:v0"` — used consistently by `markQuestComplete` and `useQuestProgress`. The v1 migration reads this same key.

**"Whoa moment" caveat:** The confetti animation only fires if `<QuestPanel />` is mounted and visible when the quest completes. If the user completes a quest on a page where the panel is dismissed or hidden, they'll see the updated checkmark on next dashboard load — not an inline animation. This is acceptable for v0. For a fully guaranteed animation, v1 can use server-sent events or polling.

**Quest panel UX:**
- Floating button: bottom-right, `z-[70]`, shows "Get Started (0/3)" — hides when all complete + 2 seconds
- Click → slide-in panel from right (320px), `AnimatePresence` from framer-motion (already in the project)
- Each quest row: emoji, title, 1-line description, "→" link button, checkmark icon when complete
- On all 3 done: `canvas-confetti` fires from inside `QuestPanel.tsx` (triggered by a `useEffect` watching `completedIds.length === QUESTS.length`, gated by a `localStorage.getItem("classmode:quest:confettiFired")` check so it fires exactly once across all page navigations — `withLayout` creates a new `Layout` instance per route, so a `useRef` alone would re-fire on every navigation; the localStorage flag persists) + panel body transitions to "You're all set! 🎉". Floating button fades out after 2 seconds. The level-up toast for Master is suppressed — the panel's "You're all set!" state is the sole celebration.
- When 7-day window expires without completion: floating button hides (same as all-complete) — determined in `use-quest-progress.ts` by comparing `Date.now()` vs `new Date(firstSeenAt).getTime() + 7 * 24 * 60 * 60 * 1000` on every read. The panel body is not shown once expired.
- Panel has an X dismiss button — sets `panelDismissed: true` in localStorage. Floating button stays visible. Pressing the button re-opens the panel (sets `panelDismissed: false`).

**Where to mount the panel:**

Add `<QuestPanel />` inside the `Layout` function's return in `client/src/App.tsx`, as a direct sibling immediately after `<Sidebar />`, before the closing `</div>`:
```tsx
// Inside Layout's return:
<div className="flex min-h-screen bg-background">
  <Sidebar />
  <QuestPanel />   {/* add here */}
  <main ...>{children}</main>
</div>
```
Mount unconditionally. Inside `<QuestPanel />`, read `profile.role` from the auth context and return `null` immediately for any role other than `teacher`. `firstSeenAt` is written on first mount (inside `useEffect(() => { if (!progress.firstSeenAt) setFirstSeenAt(now) }, [])`).

**Note on remounting:** `withLayout` creates a separate `Layout` instance per route — `<QuestPanel />` remounts on every navigation. This is safe because ALL persistent state (panelDismissed, completedIds, firstSeenAt, confettiFired) is stored in localStorage, not React state. The only React state is the `tick` counter for forced re-renders, which resets harmlessly and immediately re-subscribes to `"quest-updated"`.

**Alternative mount (if animation glitches occur):** Mount `<QuestPanel />` alongside `<Toaster />` inside `Root()` at `App.tsx:401` — survives navigation. `FirebaseAuthProvider` wraps `Root()` so `profile.role` is accessible there.

**localStorage reset (v0 edge case):** If a user clears localStorage, `firstSeenAt` resets and the 7-day window restarts. Previously-completed quests appear incomplete. Known and acceptable — the quest system is decorative, not authoritative.

### v1 Architecture (Second pass)

**DB migration:**
```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS quest_progress JSONB DEFAULT '{}'::jsonb;
-- quest_progress shape: { completedIds: string[], xp: number, level: string, completedAt: Record<string, string> }
```

**New endpoint:**
```
PATCH /api/auth/me/quests
Body: { questId: string | null, bootstrapIds: string[] }
  questId = new quest being completed, or null for migration-only bootstrap calls
  bootstrapIds = always sent; use pendingSyncIds from localStorage (empty array if none)
  Server merges questId + bootstrapIds into quest_progress.completedIds (idempotent union)
Auth: required (authenticateToken middleware)
UID: const uid = (req.session as any).firebaseUid  [same pattern as auth.ts line ~303]
Lookup: pgFindUserByAuthSubject("firebase", uid)  [matches onboarding.ts:46]
Response: { xp: number, level: string, completedIds: string[], leveledUp: boolean }
  leveledUp = newLevel !== levelFromXP(prevXP)
  prevXP = (completedIds before merging questId/bootstrapIds).length * 50
Returns 404 if user row not found.
```

**Error handling (v1 PATCH failure):** If the PATCH call fails (network error, 5xx), the client marks the quest complete in `completedIds` and adds the quest ID to `pendingSyncIds` in localStorage — user sees immediate feedback. On next mount, `use-quest-progress.ts` retries the PATCH once for each ID in `pendingSyncIds`, sending them as `bootstrapIds`. On a successful retry, `pendingSyncIds` is cleared and `syncedToServer` is set to `true`. Retry is bounded to once per mount (no infinite loop). Brief localStorage/Postgres inconsistency is acceptable for a quest system.

**Level thresholds:**
- Newcomer: 0 XP (initial state, no label shown)
- Explorer: exactly 50 XP (first quest done — one level-up moment)
- Practitioner: exactly 100 XP (second quest done — keeps motivation alive between quests)
- Master: exactly 150 XP (all quests done — final celebration)

XP is always recalculated as `completedIds.length * 50` — never accumulated from separate deltas. The four possible values are 0, 50, 100, and 150.

**Level-up animation:** framer-motion scale + opacity pulse on the floating button when `leveledUp: true` in the response. Toast: "Level up! You're an Explorer 🚀" (1st quest) or "Level up! You're a Practitioner 🎯" (2nd quest). Master level (3rd quest) suppresses the toast — the panel's "You're all set! 🎉" state is the celebration.

**Migration from v0 → v1 (concrete):** On every `PATCH /api/auth/me/quests` call in v1, the client always includes `bootstrapIds: pendingSyncIds` (the localStorage `completedIds` not yet confirmed by the server). The server merges `bootstrapIds` idempotently into `quest_progress.completedIds`, calculates XP from the merged set, and returns the authoritative state. After the first successful PATCH, `syncedToServer: true` is set in localStorage — subsequent reads prefer the server response over localStorage. For the edge case where all 3 quests were completed in v0 before v1 deploys: on mount, `use-quest-progress.ts` detects `completedIds.length > 0 && !syncedToServer` and fires a single bootstrap PATCH with `{ questId: null, bootstrapIds: completedIds }` so the migration happens even without a new quest event.

## Prerequisites (fix before wiring quest 1)

**Test creation auth bug (server/routes/tests.ts:27):** The route checks `testData.teacherId !== req.session.userId`. `req.session.userId` is the numeric Postgres `users.id`. The frontend sends `teacherId: currentUser.user.uid` which is a Firebase UID string — these never match, returning HTTP 403 for every teacher test creation. Quest 1 (`quest:create-test`) will never fire `onSuccess` until this is fixed. Fix options:
- (A) Change the frontend to send `teacherId: req.session.userId` (numeric) — but the frontend doesn't know its own numeric ID without an API call
- (B) Change the server check to use `req.session.firebaseUid` and compare against a `firebaseUid` column on the test or user row  
- (C) Simplest: remove the `teacherId !== session.userId` check entirely and derive `teacherId` server-side from `req.session.userId` (already authenticated, so the session is trusted)

Option C is the safest short-term fix — the server already knows who the teacher is from the session. Set `testData.teacherId = req.session.userId` server-side instead of trusting the client value.

## Open Questions

1. For v1: `PATCH /api/auth/me/quests` will need a new db helper `pgUpdateUserQuestProgress(userId, questProgress)` — add it to `pg-queries.ts` with a raw SQL `UPDATE users SET quest_progress = $1 WHERE id = $2`. The existing `pgUpdateUser` helper's `columnMap` does not include `quest_progress`.

## Success Criteria

1. A new teacher can complete all 3 quests without any verbal explanation — pure self-service.
2. Completion of all 3 quests = confetti fires + panel transitions to "You're all set!" without any user-visible errors.
3. Quest state persists after page refresh (localStorage v0, Postgres v1).
4. Panel doesn't show after 7 days from `firstSeenAt` (the first time `<QuestPanel />` renders for that user), unless all quests are already done — whichever comes first.
5. Zero layout shift — the floating button doesn't push other UI elements.
