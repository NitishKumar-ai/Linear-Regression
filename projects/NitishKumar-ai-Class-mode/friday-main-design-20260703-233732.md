## Problem Statement

Class-mode's entire wedge is one sentence: **"parents know within 5 minutes when
their kid is absent."** The pipeline that delivers it is built end-to-end except
the last inch, and that last inch is built wrong in a way that will not fail until
a real parent is on the other end.

`server/services/whatsapp.ts:70` sends `type: "text"` — a freeform WhatsApp
message. Meta's WhatsApp Business Cloud API only permits freeform text inside a
24-hour window that the **recipient** opens by messaging the business first. An
absence alert is business-initiated by definition (the parent did not text you),
so Meta requires a pre-approved **template** message. A freeform absence alert to
a parent who has not messaged you in the last 24h is rejected (error 131047,
"message outside the allowed window").

The failure is invisible today because of a second issue: `whatsapp.ts:52-56`
returns `success: true` and marks the send `simulated` whenever credentials are
absent (dev/test/CI). Every test passes, every founder-driven demo passes, and the
first real failure happens with a live parent. This is a false-done state — the
code looks shipped.

A third detail the automated path must reconcile: the alert body is currently a
hardcoded string built by `absenceMessage()` in
`server/services/notifications-consumer.ts:32-34`. When the automated path lands,
that copy stops being freeform text and becomes the **source of the template
parameters** — the wording submitted to Meta and the wording the code sends must
match exactly, or Meta rejects the send. `absenceMessage()` is therefore the single
source that both the Meta submission and the `type:"template"` payload derive from.

"Make the wedge production-ready" therefore means two things on different axes:
(1) build the automated template path so real schools get automated alerts at
scale, and (2) don't let Meta's multi-day verification clock block learning whether
parents even value the alert. The design does both: automated pipe as the
production target, a concierge (manual-send) bridge to validate demand this week,
and Meta business verification kicked off in parallel so its slow clock runs in the
background instead of on the critical path.

## Demand Evidence

None recorded. No real school uses the product; the "pilot school" is a seeded
simulation (`server/scripts/seed-pilot.ts`). This is unchanged from the Pilot-Proof
doc and remains the largest open risk. The concierge bridge in this design exists
precisely to produce the first real demand signal (a parent reacting to a real
alert) **before** spending days on Meta infrastructure. `pgTrackFeatureUsage(
"attendance_notify")` already fires at `server/routes/attendance.ts:89` and is the
instrument: a teacher marking attendance daily is the signal, silence is the answer.

## Status Quo

Target school (Indian K-12 — implied by the ₹-denominated fees and WhatsApp-first
parent loop): attendance lives in a paper register; parents learn about an absence
at day's end, or never; there is no fast channel from "kid didn't show up" to "a
parent's phone." The absence alert is the thing schools cannot do themselves
without a person manually texting every parent. That manual work is exactly what
the concierge bridge mimics for one school, and exactly what the automated pipe
replaces at scale.

## Target User & Narrowest Wedge

- **Target human (still to be named — the standing Pilot-Proof assignment):** a
  principal or administrator at one specific school who personally answers to
  parents when a child is absent and unaccounted for.
- **Narrowest wedge (built, plumbed, one inch from working):** teacher marks
  attendance → app computes absentees-with-parent-phone → alert to the parent's
  WhatsApp within minutes. The plumbing already works: `attendance.ts:84-86` builds
  the absentee list filtered on `parentPhone`; the durable Redis event bus (or
  inline fallback) routes it; `server/services/notifications-consumer.ts:45` calls
  `whatsappService.sendMessage`. Only the send format is wrong.

## Premises

1. **The automated template pipe is the only production-ready path** for
   business-initiated absence alerts to real parents at scale; the current freeform
   `type:"text"` send is not production-ready and will be rejected by Meta. (Agreed)
2. **The 2026-07-07 template deadline is not the pilot's critical path.** Pilot #1's
   job is to learn whether parents value the alert; that can be validated this week
   by the founder manually forwarding the alert from a personal phone, with zero
   Meta dependency. (Agreed)
3. **Meta business verification is a no-regret background task** to start
   immediately regardless of the concierge decision, because its clock is the slow
   one and building the pipe later is blocked on it. (Agreed)
4. **The consent flag is required for the automated path** (Meta opt-in policy; a
   downgraded quality rating throttles/blocks the number) but is **not** required
   for one-school concierge sends. (Agreed)

## Competitive Landscape (added via /autoplan User Challenge)

WhatsApp parent-notification, including absence alerts, is **table-stakes in Indian
K-12, not a moat.** Incumbents that already ship it: Teachmint (free, WhatsApp-native,
large distribution), Entab, MShiksha, Classplus, and dozens of local school ERPs.
Meta Utility-template messaging is a documented, week-one integration for any of them.
Implication for the wedge: "parents know within 5 minutes" is not differentiated on
its own. The defensible angle, if one exists, is elsewhere — hyper-local language,
a specific board's compliance workflow, or a job the big players ignore — and finding
it is part of the demand assignment below, not an assumption to carry.

## Buyer Premises (surfaced by review, to be tested — not assumed)

These are load-bearing and currently unverified. The demand assignment targets them:

1. **The buyer is the school (principal/admin), not the parent.** A parent reacting to
   a free forwarded alert is near-zero signal on willingness to pay.
2. **The principal's acute pain may be fees/enrollment, not absence.** Absence alerts
   could be a parent's nice-to-have rather than the buyer's must-have.
3. **Parents may already know about absences** (gate drop-off, school-run vans), which
   would blunt the "5-minute alert" value.

## Approaches Considered

### Approach A: Concierge-only (minimal viable, validation-first)
Add a read-only "parents to notify" surface: when a teacher saves attendance,
surface the absentee list with parent phones (and a copy-ready message) so the
founder sends each alert by hand from a personal WhatsApp. No Meta send, no
template, no consent column, no WABA. `attendance_notify` usage already tracks the
signal.
- Effort: S (human ~half a day / CC ~1-2 hrs). Risk: Low.
- Pros: Zero Meta risk; validates parent demand this week; nothing to break in
  front of the pilot school; fully reversible.
- Cons: Not automated (founder is the runtime); does not survive past one school;
  leaves the false-done `type:"text"` code in place as a live trap.
- Reuses: attendance absentee computation, `feature_usage` instrument.

### Approach B: Automated template pipe (ideal architecture, production target)
Build the real thing: submit a Utility-category template to Meta, change the send
payload to `type:"template"`, add a `whatsapp_consent` opt-in flag gating sends,
and remove/harden the simulate-on-missing-credentials trap so a misconfigured
production send screams instead of returning success.
- Effort: M (human ~3-5 days incl. Meta review waits / CC ~half a day of code;
  the wall-clock is dominated by Meta verification + template review, not code).
  Risk: Med — gated on external Meta approvals with variable timing.
- Pros: The only path that is production-ready at scale; automated, no human in the
  loop; kills the false-done trap.
- Cons: Blocked on Meta verification/approval timing; wasted if parents turn out
  not to value the alert (which the concierge step is designed to check first).
- Reuses: entire existing pipeline (event bus, consumer, `sendMessage` shell).

### Approach C: Concierge bridge + parallel pipe build (chosen — sequenced hybrid)
Start Meta business verification + Utility template submission **today** (Approach
B's slow external clock, running in the background). Ship Approach A's concierge
surface for pilot #1 to validate demand this week. When verification clears and the
template is approved AND the concierge signal shows parents care, land Approach B's
code (template payload + consent flag + kill the simulate trap) and cut over from
manual to automated. Neither path blocks the other.
- Effort: A + B, sequenced. Risk: Low on the learning path, Med on the automation
  path (isolated to external timing).
- Pros: Takes the 4-day template deadline off the critical path while still starting
  the Meta clock; validates demand before investing in infrastructure; ends at the
  production-ready automated system.
- Cons: Two code touches instead of one; requires discipline to not skip the
  concierge validation and jump straight to building the pipe.

## Recommended Approach

**Approach C.** It is the only option that is honest about the two axes the user's
question ("which is production-ready?") exposed. Approach B is the sole
production-ready *system*, but shipping it first bets days of Meta-gated work on
unvalidated demand. Approach A validates demand but is not a product. C sequences
them so the slow external clock (Meta verification) runs in the background from day
one, the concierge step buys the real "do parents care" answer this week, and the
production pipe lands only once both the approval and the demand signal are in hand.
Recommended because it removes the self-imposed deadline pressure without abandoning
the production target.

## Open Questions

- **Q1 (demand):** Does a real parent react to a real absence alert? Unresolved
  until the concierge step runs with one school. This is the whole point.
- **Q3 (named human):** Still unnamed — carries over from Pilot-Proof. The concierge
  step is impossible without one named principal who lets you watch attendance.
- **Template language(s):** Absence-alert body copy and language code(s) — English
  only for pilot #1, or a regional language the parents actually read? Affects the
  template submitted to Meta.
- **WABA status:** Is a WhatsApp Business Account + verified number already set up,
  or does business verification start from zero? Determines whether the long-pole is
  days or longer.
- **Consent capture point:** Where in the flow does a parent opt in? The natural
  place is the PATCH parent-phone route (`attendance.ts:245`, which today sets
  `parentPhone` via `pgUpdateUser`); the `whatsapp_consent` boolean would ride
  alongside it there. **Enforcement layer:** the gate belongs in the absentee
  filter at `attendance.ts:84-86` (add `&& s.consent` next to the existing
  `&& s.parentPhone`), so an unconsented parent never enters the send payload at
  all — same shape as the tenant scoping already applied there. Gating at the send
  site instead would let unconsented recipients reach the consumer and rely on a
  second check; filter-site enforcement is fail-closed by construction.

## Distribution Plan

Web service on the existing GitHub Actions → Cloud Run pipeline; no new distribution
channel. The only external "distribution" is Meta approval of the WABA number and
the Utility template — a prerequisite, not a code artifact. Absence alerts must be
real (not simulated) for the pilot's automated phase; the simulate path stays only
as an explicit dev/test affordance, never a silent production fallback.

## Dependencies

- **Meta WABA + Business Verification** — start immediately; slow clock; gates the
  automated path entirely.
- **Meta-approved Utility template** — submit this week; body with placeholders for
  student name, date, school name; Utility category (cheaper/faster to approve than
  Marketing, and free inside an open conversation).
- **`whatsapp_consent` opt-in** — new boolean on the student/parent record, default
  false; no automated send unless true; collected at parent-phone entry.
- **Kill the simulate-on-missing-credentials trap** — `whatsapp.ts:52-56` must not
  return `success:true` in production when credentials are missing; it should error
  and alert.
- **One named real school** — founder's job, no code dependency; blocks the
  concierge step and therefore the whole sequence.

## The Assignment (reweighted demand-first — accepted User Challenge, 2026-07-04)

**One move this week: prove a buyer, not a pipe.** Meta verification, the consent
schema, and the automated template path are all **paused** until a principal says
absence alerts are why they'd pay.

1. **Name one principal and get a yes** to a 30-minute session where you watch a
   teacher mark attendance. Not a demo you drive — a session you watch.
2. **In that session, test the buyer premises, not the parent's reaction.** Forward
   the absence alert from your own WhatsApp (concierge — no Meta dependency), but the
   signal you are hunting is the *principal's*: do they ask "can this run
   automatically?" unprompted, agree to a paid pilot, or hand you a second class
   without you pushing? And critically — **would they pay for absence alerts, or do
   they want fee reminders / something else first?**
3. **Ship only the two cheap-and-correct code tasks now** (independent of the
   strategy answer): T1 (make the simulate-success trap fail loud in production; add
   a `sendTemplate` scaffold) and T6 (first tests for the notify path, which today
   has zero). Everything else in the build list waits.

If ten asks yield zero yeses, that is the most valuable data of the week — and it
likely means absence-alert is not the wedge (fees may be). Do not start Meta
verification or write the consent schema on spec.
