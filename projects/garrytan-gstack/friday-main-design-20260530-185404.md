## 1. System Architecture & Layers
CommitGuard v3 operates as a four-tier pipeline:
* **L1 — Candidate Scanner:** Gemma 2 9B IT model scanning repository directories. Uses Repository Language Model (RLM) scaffolding to recursively query file maps, construct symbol graphs, and propose vulnerability candidate files.
* **L2 — Sandbox Verifier:** Prompts the same base model (in exploit-writer role) to write and execute python/bash proof-of-concept exploits against the target application inside a secure, isolated sandbox.
* **L3 — Auto-Documentation Pipeline:** Automatically converts confirmed findings (and failed attempts) into structured training pairs.
  * **Schema/Format:**
    ```json
    {
      "code": "vulnerable_code_snippet", // The specific function containing the vulnerability, capped at 100 lines, including immediately preceding context.
      "cwe": "CWE-89",
      "verdict": "CONFIRMED | UNEXPLOITABLE_FP | SYNTAX_ERROR",
      "exploit_code": "poc_exploit_script",
      "exploit_output": "stdout_or_error_logs",
      "fix": "remediation_recommendation",
      "repo": "github.com/user/repo",
      "commit": "sha256_hash"
    }
    ```
  * Uploads these pairs to a Google Cloud Storage (GCS) bucket.
* **L4 — Self-Training Trigger:** Orchestrates LoRA adapter retraining once a training sample delta threshold is reached. During the initial phase, retraining, safety gate verification, and deployment are done offline/manually rather than fully automated in production.

## Problem Statement
Standard static analysis security scanners suffer from high false positive rates and cannot reliably determine if a code snippet is actually exploitable in practice. This leads to wasted developer time triaging noise. At the same time, manual vulnerability verification and exploit writing do not scale.

## What Makes This Cool
CommitGuard v3 attempts to exploit candidate vulnerabilities in a secure, isolated runtime sandbox. This generates its own ground truth: if the exploit succeeds, it files a high-confidence GitHub issue; if it fails, it discards it. These verified findings are automatically formatted and fed back into a GCS bucket, triggering a self-training loop (LoRA fine-tuning) that improves the scanner model autonomously over time. It is a self-improving code security loop with zero human labeling bottleneck.

## Constraints
* **Inference Platform:** Must run within a persistent US-Central1 L4 GPU VM environment.
* **Sandbox Security & Performance:** The execution sandbox must block external network egress, enforce 30s timeouts, limit RAM to 2GB per job, and operate on a read-only filesystem clone.
* **Fidelity Requirements:** Exploit verification must target fully initialized, running applications (ports bound, databases seeded) rather than simple stub functions.

## Detailed Design & Refinements

### Sandbox Life Cycle & Dependency Management
To resolve the conflict between package downloading (requires network) and exploit safety (requires zero network egress), application sandboxing runs in a two-stage lifecycle:
1. **Stage 1: Build Phase (Egress Allowed, Sandboxed):** The sandbox orchestrator reads dependencies (e.g., `package.json`, `requirements.txt`). This phase is fully sandboxed with egress restricted to trusted registries (npm and PyPI package mirrors). Custom setup scripts (like `.commitguard/setup.sh`) are disabled in the initial build stage to prevent arbitrary host code execution or metadata exfiltration. Secure credentials for private package registries (e.g., `.npmrc` or PyPI credentials) are injected as build-time secrets and scrubbed before Stage 2.
2. **Stage 2: Exploit Verification Phase (Egress Disabled):** The pre-built image runs inside a container isolated by **gVisor (runsc)**. Egress is disabled, except for a restricted local loopback network.

### Sandbox Lifecycle Hooks & Resource Cleanup
The sandbox orchestrator executes three lifecycle hooks:
* `setup()`: Configures the isolated network namespace, sets up SQLite or in-memory databases (or an ephemeral single-container Postgres/MySQL database if specified in the config), and executes standard framework migration commands (e.g., `npm run db:migrate`, `python manage.py migrate`).
* `run()`: Executes the exploit payload against the application using the local environment variables.
* `teardown()`: Executes a hard cleanup cycle. It forces the deletion of all containers, network namespaces, and databases associated with the specific job ID, ensuring zero port collisions or resource leaks on the host.

### Database Instantiation & Concurrency Isolation
* **Database Isolation:** To support high-fidelity database-specific dialects (e.g. Postgres-specific JSONB queries), applications can specify an ephemeral database sidecar (e.g., Postgres, MySQL) inside the target's `.commitguard.yaml` configuration. For standard applications using abstraction layers (ORMs like Sequelize, Django ORM, SQLAlchemy), the sandbox defaults to SQLite/in-memory databases.
* **Concurrency:** Each exploit job runs in its own private namespace. The L2 exploit code executes inside the same isolated namespace as the target application, allowing it to reach the service over loopback (`localhost:8080`) without exposing host ports.
* **Mount Layout:** The application root is read-only, but `/tmp` is mounted as a writable, ephemeral `tmpfs` volume to support log generation and temporary file manipulation.

### Verification Heuristics & Success Criteria
The verifier validates exploit success by observing concrete side-effects in the sandbox:
* **Arbitrary Code Execution / RCE:** Writing a specific flag file (e.g., `touch /tmp/compromised.flag`) and checking for its existence.
* **SQL Injection (CWE-89):** Injecting payloads and verifying structural data bypass (e.g., retrieving restricted table contents returned in stdout/JSON).
* **SSRF (CWE-918):** Exposing a local HTTP request sink (mock service) on loopback. If the app sends an HTTP request containing a unique hash to this mock service, the verifier confirms the SSRF exploit succeeded. The mock service is managed by the sandbox orchestrator inside the loopback network namespace, and its location is exposed to the application via the `SSRF_SINK_URL` environment variable.
* **Standardized Auth Injection:** Target codebases must define test authentication bypass hooks or override configuration variables (e.g., `TEST_API_KEY`) inside `.commitguard.yaml`. The sandbox injects these variables directly into the application environment.
* **Exploit Repair Loop:** 9B models are prone to script errors. If the L2 exploit script encounters a runtime or syntax error, the orchestrator captures the traceback, feeds it back to the model, and allows up to 2 repair attempts.

### Exploit Targets and Environment Injection
The orchestrator communicates targeting and connection variables directly into the L2 exploit writer agent using environment variables:
* `TARGET_URL`: The local loopback URL (e.g., `http://localhost:8080`).
* `DB_CONN_STRING`: Connection details to the SQLite file path or ephemeral database instance inside the container namespace.

### Self-Training Validation & Safety Gate
1. **Retraining Trigger:** The training orchestrator monitors the GCS bucket. When the new training pairs (both positive verified exploits and negative failed attempts) reaches 500, a LoRA fine-tuning run is triggered.
2. **Negative Feedback Signal:** The dataset records both successful exploits (`CONFIRMED`) and failed attempts (`UNEXPLOITABLE_FP`, `SYNTAX_ERROR`) to teach the model to distinguish between exploitable paths and non-exploitable false positives.
3. **Safety Gate Check:** The newly generated LoRA adapter must pass an automated dynamic regression test suite (verifying exploitability against 100 historical CVE test cases) with a minimum detection score of 95% and zero regressions.
4. **Gate Failure Handling:** If validation fails, the orchestrator logs the regression error, quarantines the latest 500 samples for manual review, rolls back the active model adapter to the previous stable state, and flags the build run as failed.
5. **PEFT Weight Swapping:** PEFT dynamic reloading (using `peft.PeftModel.load_adapter` via FastAPI `/reload` endpoint) is designed as target architecture for Phase 2; Phase 1 uses standard offline model training and container restarts.
6. **De-scoped Integrations:** PagerDuty/Slack alerts are de-scoped from the initial phase in favor of local console logging and diagnostic reports.

## Premises
1. Closed-loop verification (L2 sandbox execution) provides near-zero false positive rates by running actual exploits.
2. Dynamic application instantiation inside container-native gVisor sandboxes can be performed reliably using environment configuration files (`.commitguard.yaml`) and dependency locks.
3. Retraining on verified dynamic exploit verification runs (including failed attempts) will steadily improve Gemma 2 9B's vulnerability identification capabilities without catastrophic drift.

## Approaches Considered
### Approach A: Ephemeral Docker & Local File Taint (Minimal Viable)
Stubbing function targets and executing python exploits against local unit-test-like mocks inside a lightweight Docker container. Low overhead but lower verification fidelity.
* **Effort:** Small
* **Risk:** Medium
* **Pros:** Fast execution speed, runs on standard VMs, low resource usage.
* **Cons:** Misses complex exploits that require live server ports.
* **Reuses:** Docker Python SDK.

### Approach B: gVisor Container Sandbox with Environment Instantiation (Ideal Architecture)
Instantiating the full application container stack in a secured gVisor container runtime namespace and executing the LLM-generated exploit code against the live local endpoints. Maximum verification fidelity but high complexity.
* **Effort:** Large
* **Risk:** High
* **Pros:** Maximum fidelity, catches logical and network exploits, absolute sandbox isolation.
* **Cons:** Slow startup times, high infrastructure setup complexity.
* **Reuses:** gVisor (runsc).

### Approach C: Static Taint Tracing + Symbolic Mocking (Creative/Lateral)
Using constraint solvers (Z3) to mathematically prove exploitability along paths instead of code execution. Extremely safe but very complex to model dynamic runtime structures.
* **Effort:** Medium
* **Risk:** High
* **Pros:** Safe (no code execution needed), precise mathematical constraints.
* **Cons:** Hard to write solvers for arbitrary dynamic code paths.
* **Reuses:** Z3 solver.

## Recommended Approach
Approach B (gVisor Container Sandbox) because the team prioritized maximum fidelity and absolute sandbox isolation (using gVisor) to safely and reliably capture the full spectrum of exploits (Logical, SQLi, SSRF, RCE).

## Open Questions
* How can we dynamically configure database connections or external dependencies (like key-value stores or third-party APIs) during microVM instantiation?
* What threshold of new verified training pairs (e.g. `RETRAIN_THRESHOLD = 500`) offers the best trade-off between model improvement rate and training cost/compute?

## Success Criteria
* Execution of a fully automated loop: raw repository URL input -> L1 candidate scanning -> L2 sandbox verification showing a successful exploit proof -> L3 auto-documentation GCS upload -> L4 retraining trigger.
* Verified finding false-positive rate under 1%.
