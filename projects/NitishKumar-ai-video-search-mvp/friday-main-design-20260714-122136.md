## Problem Statement
The user wants to build a natural language video extraction tool to semantically search and retrieve matching clips from recorded video archives using NLP and Vision.

## What Makes This Cool
Combining video, audio, and object tag metadata locally so users can search for complex physical descriptors and audio cues (e.g., "screaming near the north gate") with zero cloud connectivity, producing an instant visual timeline and downloadable clip segments.

## Ingestion & AI Processing Flow
1. **Video Ingestion Entry Point**: Videos are uploaded via a REST API endpoint (`POST /api/videos/upload`) or placed in an ingestion directory. Raw videos are saved to `/uploads/` and an asynchronous ingestion task is triggered in Celery.
2. **Celery Worker Pipeline**:
   - **Video Demuxing**: FFmpeg samples frames at a fixed 1 FPS rate.
   - **Audio Demuxing**: FFmpeg extracts the audio track, and Whisper processes the transcription.
   - **Visual Embeddings**: Sampled frames are processed by a standard CLIP model (ViT-B/32) running locally (using CUDA on Linux or MPS on Apple Silicon, falling back to CPU). Bounding boxes and labels are computed using a lightweight YOLOv8n model.
   - **Data Indexing**: Frame embeddings are indexed in Qdrant; Whisper transcripts, YOLO tags, and camera metadata are written to PostgreSQL.

## Databases
### PostgreSQL Schema
- `videos` table:
  - `id`: UUID (Primary Key)
  - `filename`: VARCHAR(255)
  - `filepath`: VARCHAR(512)
  - `camera_id`: VARCHAR(100) (Indexed)
  - `created_at`: TIMESTAMP (Default: now())
  - `duration`: FLOAT (in seconds)
  - `status`: VARCHAR(50) (e.g., 'processing', 'completed', 'failed')
- `segments` table:
  - `id`: UUID (Primary Key)
  - `video_id`: UUID (Foreign Key -> `videos.id`)
  - `start_time`: FLOAT (in seconds)
  - `end_time`: FLOAT (in seconds)
  - `yolo_tags`: JSONB (list of objects with counts, e.g. `[{"label": "person", "count": 2}]`)
- `transcripts` table:
  - `id`: UUID (Primary Key)
  - `video_id`: UUID (Foreign Key -> `videos.id`)
  - `start_time`: FLOAT (in seconds)
  - `end_time`: FLOAT (in seconds)
  - `text_segment`: TEXT (Whisper transcribed segment)

### Qdrant Vector DB Schema
- **Payload Metadata**:
  - `video_id`: (string) matches PostgreSQL record
  - `camera_id`: (string) matches camera source
  - `timestamp`: (float) timestamp of the sampled frame

## API Contracts
### `POST /api/videos/upload`
- **Request**: Multipart form data with `file` (MP4/MOV) and `camera_id` (string)
- **Response**: `{"video_id": "uuid", "filename": "example.mp4", "status": "processing"}`

### `GET /api/search`
- **Request Parameters**:
  - `q` (string): Natural language search query
  - `camera_id` (string, optional): Filter by source camera
  - `start_time` (float, optional): Relative search window start (seconds)
  - `end_time` (float, optional): Relative search window end (seconds)
- **Response**:
  ```json
  {
    "query": "person in red shirt",
    "results": [
      {
        "video_id": "uuid",
        "camera_id": "gate-north",
        "start_time": 45.0,
        "end_time": 55.0,
        "score": 0.82,
        "clip_url": "/api/videos/uuid/clip?start=45.0&end=55.0"
      }
    ]
  }
  ```

### `GET /api/videos/{video_id}/clip`
- **Request Parameters**: `start` (float), `end` (float)
- **Response**: Streaming MP4 video chunk (dynamic FFmpeg cut, cached locally in a temporary directory via an LRU cache eviction policy to prevent disk bloat).

## Constraints & Model Choices
- **Hardware Optimization**: To run efficiently on CPU/GPU Docker hosts, we default to:
  - Visual embedder: standard CLIP (ViT-B/32)
  - Object detector: YOLOv8n (using ONNX runtime for CPU execution optimization)
  - Audio transcription: Whisper `base` model
- **Privacy Compliance**: No cloud networks are contacted; all weights are downloaded once during Docker build/first run and cached in a Docker volume.

## Premises
1. **Focus on local multi-modal pipeline rather than cloud-hosted APIs**: Keeping video/audio processing entirely local is a hard requirement because investigators handle sensitive surveillance data that cannot be sent to cloud networks.
2. **Re-use existing FastAPI and Celery worker layout**: Instead of scaffolding a new system from scratch, we should implement the search and clip extraction endpoints inside the existing FastAPI app (`api/`) and orchestrate frame extraction and AI indexing via Celery (`workers/`).
3. **Database Schema supports camera ID filtering**: Rather than treating video frames as independent images, our vector search index and relational DB carry metadata links for `camera_id` and timestamps, allowing search results to be filtered by camera source.

## Approaches Considered
### Approach A: Minimal Viable (Frame CLIP + Fast-Cut FFmpeg)
- **Summary**: Extracts frames at a fixed interval (1 FPS) and embeds them using CLIP. A search endpoint accepts text queries, queries Qdrant, returns the best-matching frames, and clips the source video dynamically into 10-second segments around those frame timestamps using FFmpeg.
- **Effort**: S (human: ~1 day / CC: ~10 min)
- **Risk**: Low
- **Pros**:
  - Extremely fast to implement; requires minimal edits to Celery workers and API.
  - Returns direct video clip downloads using simple FFmpeg seek cutting.
- **Cons**:
  - No audio search (Whisper) or precise object count filters.
  - Heavy video segment rendering on the fly can slow down concurrent API requests.
- **Reuses**: Existing video ingestion frame slicing logic and vector DB client.

### Approach B: Ideal Architecture (Multi-Modal Event Graph & Segment Cache)
- **Summary**: Ingestion runs video frames through CLIP/SigLIP and YOLO, and extracts audio to Whisper. Extracted metadata (transcripts, camera ID, YOLO bounding boxes, and embeddings) is stored in Postgres and Qdrant. A segment extraction service generates indexable clip chunks (e.g., scene-based or 10s intervals) and caches them in local storage. The query parser decomposes natural language into visual, audio, and camera-metadata terms, performing boolean-filtered vector search.
- **Effort**: L (human: ~5 days / CC: ~30 min)
- **Risk**: Medium
- **Pros**:
  - Highly accurate search utilizing visual, auditory, and object metadata.
  - Database schema isolates `camera_id` and timestamps, allowing Re-ID tracking.
  - Segment cache makes playback near-instantaneous (no on-the-fly FFmpeg cut delays).
- **Cons**:
  - Highly complex database sync between Qdrant, Postgres, and the filesystem.
  - Processing is slow on CPU-only hosts without GPU acceleration.
- **Reuses**: Celery async workers, FastAPI dependencies, PostgreSQL db session.

## Recommended Approach
Approach B (Multi-Modal Event Graph & Segment Cache) because it provides the database schema and caching layer needed to search visual embeddings, audio transcripts, and object tags, creating a convincing security tool while maintaining high performance.

## Success Criteria
1. A natural language search returns timestamped clips matching the query description within 3 seconds.
2. The system successfully plays the returned clips in the browser via `static/index.html` without buffering delays.
3. The database schema stores camera ID and frame sequences enabling camera source filtering.
